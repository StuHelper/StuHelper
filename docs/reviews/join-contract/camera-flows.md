# camera-flows

## summary
The freshman camera capture slice has three parts: (1) cameraCapture.ts — a pure browser-API utility layer wrapping getUserMedia (rear-facing camera, no audio), canvas-based JPEG frame capture to base64 with client-side size-limit enforcement, stream teardown, and a Chinese error-copy mapper keyed on DOMException names and exact English error-message strings; (2) FreshmanCameraFlow.vue — the desktop in-page flow embedded in AdmissionPage (/verify/:code) that collects school/name/dept/materialType, lazily creates a FreshmanApplication on first submit/handoff, captures+uploads camera material, and offers a desktop-to-mobile handoff via QR code (qrcode npm) whose status is tracked live via an SSE EventSource at a hardcoded path with a 1500ms polling fallback, including a cross-device locking state machine (pending/uploaded/locked[desktop|mobile]/expired) that disables desktop controls and emits submitted/expired to the parent; (3) FreshmanMobileCameraPage.vue — a standalone, auth-free route /admission/freshman/camera/:token that previews the handoff by token, captures and uploads from the phone, then lets the user choose continuation (desktop vs mobile), with rigorous stale-token/stale-response guards (a load sequence counter plus token equality checks on every async resolution) and stream cleanup on play() failure, upload success, expiry, token change, and unmount. All user-facing copy is hardcoded Chinese (no i18n), and both unit tests (vitest + @vue/test-utils with heavy browser-API monkey-patching) and Playwright e2e tests assert on data-attributes, button class names/DOM order, role+accessible-name (Chinese text), exact API paths/payloads, and the SSE URL.

## rewrite_risks
- Desktop vs mobile openCamera asymmetry: FreshmanCameraFlow does NOT stop the acquired MediaStream when video.play() rejects (stream.value stays set, 拍摄 button appears, camera LED stays on); FreshmanMobileCameraPage DOES stop it and reverts to the open button. A unified camera composable will silently change desktop behavior; only the mobile behavior is test-covered, so the regression would ship unnoticed
- applyFreshmanCameraHandoff stale guard requires BOTH nextHandoff.id===expectedHandoffID AND handoff.value?.id===expectedHandoffID (FreshmanCameraFlow.vue:401-406). Simplifying to a single-sided check re-admits stale SSE events from a previous (expired/regenerated) handoff — covered by unit test 'ignores stale SSE events after regenerating a mobile handoff' which keeps emitting on the OLD FakeEventSource instance after a new one is created
- emit('submitted') fires on locked status for BOTH continueOn values, including 'mobile' (desktop UI is 'locked' yet the parent transitions to 等待管理员审核). This is counterintuitive — a rewriter may 'fix' it to desktop-only and break the 'locks desktop controls when mobile continuation is chosen' test. Also note the payload is application.value (the created application), whereas the direct-submit path emits the reviewed application returned by uploadCameraCapture — different objects
- submissionEmitted is a plain module-scoped-in-setup let guarding only the handoff-locked emit; submitFreshmanMaterial emits without checking/setting it. Double-emit is possible (locked+desktop does not disable the submit button) but in production the parent unmounts on first emit. Changing emit ordering or adding the guard to the submit path changes observable unit-test behavior
- EventSource semantics: feature detection is typeof window.EventSource !== 'function' (degrades straight to polling); onerror permanently abandons SSE for 1500ms polling (native EventSource would auto-reconnect — the code deliberately closes instead). e2e asserts pollingRequests===0 when SSE succeeds and unit asserts close() called exactly once on failure; a 'smarter' reconnect strategy breaks both. The SSE path is a hardcoded relative URL with encodeURIComponent(handoffID), cookie-auth only — not built from the API client baseURL
- handleFreshmanCameraHandoffLockedError control flow is subtle: it refreshes the handoff FIRST, and that refresh can itself emit submitted (via apply seeing status locked) before the branch logic reads handoff.value — the locked+desktop branch then merely clears the error and relies on the side effect. Linearizing this into explicit branches easily drops the emit or double-emits
- Stale-async gating on the mobile page has two distinct mechanisms that must both survive: handoffLoadSeq (monotonic counter, also bumped in onBeforeUnmount to kill in-flight loads) for previews, and token-equality checks (isCurrentMobileToken) for openCamera/upload/continuation. The finally blocks deliberately do NOT reset uploading/choosing when the token changed — resetHandoffStateForTokenLoad does it; restructuring with naive finally{flag=false} reintroduces a race the tests target
- Mobile openCamera re-checks pageState==='ready' AFTER the getUserMedia await (the state may have moved to uploaded/expired during the permission prompt) and stops the just-acquired stream — dropping this leaks a live camera track
- captureFrameAsBase64 must keep using document.createElement('canvas') + canvas.toDataURL + a real <video> element with videoWidth/videoHeight: unit tests spy on document.createElement and HTMLCanvasElement.prototype.getContext/toDataURL, and e2e addInitScript patches the same prototypes. OffscreenCanvas, createImageBitmap, ImageCapture API, or canvas.toBlob would all break the test harness; toDataURL quality 0.92 and default 'image/jpeg' feed directly into asserted request bodies
- maxBytes sources differ by surface: desktop uses props.maxMaterialBytes (from AdmissionSession.maxMaterialBytes, optional — undefined disables the check); mobile uses handoff.maxMaterialBytes (required field from the handoff response). Swapping or centralizing these changes enforcement (e2e sets them to different values per test); the byte estimate is computed on base64 length, not the decoded blob
- supportsCameraCapture is sampled once into a ref at setup; the disabled '当前浏览器不支持摄像头' button is the contract when navigator.mediaDevices is undefined (e2e sets it via addInitScript BEFORE app boot). Making it reactive or re-checking per click is a behavior change; conversely the desktop openCamera path still re-validates via startCameraStream's throw
- DOM-order coupling: cameraCapture.test.ts clicks wrapper.get('button.secondary-button') (first match) to mean open-camera and then 拍摄 — the camera buttons must keep class 'secondary-button' AND precede the mobile-handoff button (same class) in source order; submit must remain a type='submit' button inside the <form @submit.prevent> (tests trigger('submit') on form directly)
- Vue scoped-CSS quirk: .primary-button/.secondary-button styling lives in AdmissionPage's scoped stylesheet and cannot reach FreshmanCameraFlow's inner elements or the standalone mobile page — these buttons are effectively unstyled today. In a rewrite, keep the class names regardless (test selectors) and decide consciously whether to actually style them; 'fixing' styling is fine, removing the classes is not
- The watch on props.schools (immediate) silently resets schoolCode to the first school whenever the current selection disappears from the list; e2e relies on auto-preselect of the single school. Lazy initialization or v-model refactors must preserve auto-select-first and keep-if-still-present semantics
- applicationLocked freezes all four form fields permanently once ensureFreshmanApplication succeeds (even if a later upload fails) — there is no edit-after-create path; do not add one
- Locked-handoff error detection is message-substring based (/handoff locked/i) with code 'A0000409' in tests but the code is NOT checked — only the message; similarly the mobile not-found check accepts status 404 OR a message regex. Backend message wording is part of the de-facto contract
- Mobile route is auth-free: e2e fails if ANY **/api/v1/auth/** request fires on /admission/freshman/camera/:token. The rewrite must keep layout:'none' and avoid pulling in stores/composables that bootstrap auth (user store, /me fetches) into this page's import graph
- Timers/cleanup: polling uses window.setInterval id typed as number; onBeforeUnmount on desktop must stop the stream AND polling AND SSE (unit asserts stopTrack on unmount); mobile onBeforeUnmount must bump handoffLoadSeq and stop the stream. Vue 3 setup unmount hooks are the only cleanup — there is no visibilitychange/pagehide handling; do not add or remove lifecycle behavior
- parseHandoffEvent validates only 4 fields then casts — SSE payloads bypass api.ts's strict readFreshmanCameraHandoff validation (e.g., maxMaterialBytes may be absent from an SSE event without error). Routing SSE data through the strict validator would reject payloads the current code accepts
- Video element markup: autoplay+muted+playsinline are required for iOS Safari inline autoplay; srcObject must be set before await play(); the desktop <video> is permanently rendered (acts as black placeholder) while mobile's exists only in the 'ready' branch — moving the desktop video behind v-if changes both visuals and videoRef availability timing for captureMaterial's mounted-check throw
