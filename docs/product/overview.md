# StuHelper 产品介绍（面向内部人员版）

## 1. 产品定位

**StuHelper 是面向校园场景的“对象主页 + 订阅通知”的统一信息与服务平台。**
我们将校园中高频且长期存在的关键对象（课程、教师、教室、食堂窗口、校车站点、校园卡、办事系统入口等）抽象为一套标准化的“对象主页”。**内容、流程、服务入口、实时状态与通知**均围绕对象进行组织沉淀；用户通过“订阅对象”获取持续更新，显著降低信息搜寻与重复咨询成本。

> 一句话概括：**把校园信息从“刷时间线”升级为“找对象主页”，把变化从“靠人转发”升级为“订阅自动到达”。**

---

## 2. 目标用户与适用场景

### 2.1 面向学生（ToC）

* 课程与教师相关：评课、资料、作业/考试经验、往年题、回放入口等集中沉淀
* 学习空间与生活服务：空教室、用电、校园卡余额、校车出行、地点导航等“状态化服务”
* 校园互动：即时求助、同对象下讨论、组团拼单、校园墙等（强调有上下文、可治理）

### 2.2 面向学校与开发者（ToD）

* 为校内应用提供**统一身份标识、通知通道、订阅关系、审计日志、权限治理、策略配置、API 网关**等平台能力
* 支持学校将分散系统能力更低成本地“挂接”到同一对象体系与订阅机制上，形成长期可运营的“校园服务聚合层”

---

## 3. 核心产品能力（客户可感知的“卖点”）

### 3.1 对象主页（Entity Page）：信息沉淀的唯一入口

每一个校园对象都有自己的“主页/板块”，可承载并沉淀：

* **内容**：评价、问答、经验贴、资料、攻略
* **服务入口**：系统链接、办理入口、地图导航、充值入口
* **状态**：空闲/拥挤、余额/阈值、倒计时、开放/关闭、已解决/处理中
* **关联关系**：课程 ↔ 教师 ↔ 资料 ↔ 课堂/教室 ↔ 回放/网盘链接等

这解决了校园信息长期存在的核心问题：**信息散、重复问、难追溯**。

---

### 3.2 订阅通知（Subscription）：信息“找人”而非人“找信息”

用户可订阅课程、教室、食堂窗口、校车线路/站点、校园卡等对象。对象状态变化或内容更新时，按用户偏好进行通知推送，例如：

* 低电量提醒、校园卡低余额提醒（附直达充值链接）
* 收藏教室空闲提醒、关注课程新增资料提醒
* 校车下一班倒计时、站点变更提醒
* 求助单有新回复/已解决状态变更提醒

通知通道可按建设阶段逐步覆盖站内实时（WebSocket）到异步（邮件/服务号/短信等），并支持降级与频控。

---

### 3.3 内容形态与状态机：从“发帖”升级为“可完成的事务”

为避免校园社区天然走向“水贴/情绪广场”，StuHelper 将内容以“可治理、可沉淀”的形态呈现：

1. **现场卡（Now Card）**：短时效信息（2–24h），用于实时状态上报
2. **问题单（Issue/求助单）**：必须流转状态（求助中 → 已解决），沉淀解决方案
3. **沉淀页（Wiki/FAQ）**：可编辑、版本化、可引用，形成稳定知识资产
4. **评价/资源（Review/Resource）**：强绑定课程/教师对象页，与资料审核和激励体系打通


* 不做完整 IM，但**每个对象页提供“论坛板块”与 Wiki 沉淀能力**，实现“讨论可发生、结果可沉淀”。

---

### 3.4 “信息流”与“对象页”并存：兼顾探索与沉淀

为了满足“用户也想刷一刷”的使用习惯，StuHelper 支持：

* **最新动态页（信息流）**：展示关注对象/全站热点的更新
* **对象页（主阵地）**：所有内容最终归档到对象主页下，保证长期可检索与可复用

对外口径建议强调：**信息流用于发现，对象页用于沉淀。**

---

## 4. 平台化能力（ToD）：可接入、可治理、可运营

### 4.1 统一身份与权限（SSO + RBAC）

* 支持对接校园 SSO，提供统一用户标识
* RBAC 分层：管理员/志愿者/开发者/普通用户
* 便于实现“灰度开放、定向开放、校内部门协同治理”

### 4.2 策略配置中心（Policy Center）

用配置而不是改代码来控制：

* 功能开关、灰度、白名单、审批、回滚
* 频控、配额、风控阈值（例如订阅推送频率、敏感功能开放范围）


### 4.3 通知中心（Notification Hub）

* 统一模板、渠道路由、失败重试、降级策略
* 支持站内实时、邮件/服务号/短信等扩展
* 支持用户偏好与退订机制

### 4.4 开放平台与 API 网关

* 开发者认证、API 网关统一接入
* 对第三方提供：统一身份、订阅关系、通知投递、日志审计、事件回调
* 形成“校园能力生态”，避免各应用孤岛

### 4.5 可观测与审计

* 关键操作留痕、异常告警、行为审计
* 支持运营指标看板（增长、留存、内容质量、响应时效）

---

## 5. Agent 混合架构（可选能力，面向校园网络现实）

在校园网络环境中，部分任务存在“仅校内可访问/频率受限/需要分布式执行”的客观约束。StuHelper 支持**调度中心 + 校内节点 +（可选）客户端节点**的混合架构，用于承载：

* 校内接口对接与任务执行
* 高并发抓取/同步类任务的分流
* 受限能力的“技术原因解释”（即：网页端无法完成的能力可通过受控节点执行）

重要说明（对外口径建议）：

* Agent **不作为大多数核心功能的门槛**；仅在“确需校内/用户侧执行”的场景启用
* Agent 采用**最小权限、指令白名单、可审计**的安全策略
* 是否开源可作为商业与安全策略议题保留

## 6. 典型落地案例（建议对外演示用）

### 案例 A：课程对象页（教学场景）

* 课程页聚合：评课、往年题、资料、作业/考试经验、回放入口
* 用户订阅课程：新增资料/重要动态自动提醒
* 价值：减少重复提问，形成跨学期可复用资产

### 案例 B：空教室与学习空间（学习空间场景）

* 收藏教室，空闲/开放状态提醒
* 人流/拥挤度：优先采用低敏数据（自愿上报、热度等级）；如未来具备授权与条件，可探索“视觉统计/边缘计算”等更高精度方案（对外不建议直接说“监控 CV 数人头”，改成更合规的表述）

### 案例 C：校车与地点导航（出行场景）

* 下一班倒计时 + 时刻表导入
* 上车点/高频地点地图标记
* 价值：替代截图传播，信息统一、可更新、可订阅

### 案例 D：校园卡与失物招领（卡务场景）

* 低余额提醒 + 直达充值
* “联系失主”采用**匿名中转机制**：拾得者提交卡号 → 平台通知失主 → 双方在平台内受控沟通，避免隐私泄露与骚扰

---

## 7. 治理与风险控制（客户最关心的部分）

StuHelper 的社区与信息服务能力，内置治理机制，避免“做大后不可控”：

* 举报/审核/处罚/申诉闭环
* 积分（正向激励）与信用（惩罚约束）双体系
* 敏感能力默认关闭，受策略中心控制
* 内容与行为留痕审计，支持运营与安全管理

---

## 8. 建设路线（MVP → 扩展）

### 阶段 1：MVP（最小可用闭环）

* 课程对象页：评课 + 资料 + 课程聚合
* 订阅与站内通知
* 空教室/电费/校园卡余额 等高频便民服务
* 基础治理（举报、审核、RBAC）

### 阶段 2：对象扩展与开放平台

* 校车/地点对象、食堂窗口评价、更多生活服务对象
* API 网关与开发者接入
* 通知通道扩展（邮件/服务号/短信等）

### 阶段 3：智能化与自动沉淀

* 自动摘要与 FAQ/Wiki 草稿生成
* 对象页内检索增强
* 辅助审核与风控
* 高成本多模态（如直播事件识别）作为探索项，按资源与授权推进

---

# 附：对外“差异化”三句话（适合 PPT 扉页）

1. **对象主页：让校园信息沉淀，而不是随时间流失。**
2. **订阅通知：让更新自动到达，而不是靠人转发。**
3. **平台底座：统一身份、通知、策略与开放接口，支持校园应用生态接入。**
