# 学生认证与群聊入群准入系统

## 1. 文档定位

本文定义 StuHelper **目标态**的学生认证、学校认证适配、学籍快照、人工审核，以及群聊入群准入
之间的产品边界和验收规则。

本文状态为 `draft`，不表示下述能力已经全部实现。实施完成前：

- 当前 API 仍以 `server/api/openapi.yaml` 为准；
- 当前数据库结构仍以 `server/migrations/` 为准；
- 当前运行时行为仍以源码和测试为准；
- 当前用户认证行为见 [用户系统](user-system.md)；
- 当前 QQ 入群链路见 [入群认证流程](../design/admission-flow.md)。

本文使用以下规范词：

- **必须**：上线和验收不可缺少；
- **应当**：默认必须满足，只有记录了明确理由才可偏离；
- **可以**：由学校、消费方或部署策略选择启用；
- **不得**：明确禁止。

所有具备上线约束或验收意义的条款均使用稳定 ID。流程图、示例和解释性文字用于帮助理解，不覆盖
带 ID 的条款；ID 分配和追溯矩阵治理规则见 `TRACE-001`、`TRACE-002`。

## 2. 产品结论

### 2.1 核心决策

1. `DEC-001`：**学生认证是独立业务域**，用于证明某个 StuHelper 账号当前具备某所学校的学生身份。
2. `DEC-002`：**QQ 绑定是独立的平台账号绑定域**，用于证明某个 StuHelper 账号控制某个 QQ 号。
3. `DEC-003`：**群聊入群准入是认证结果的消费方**。群策略可以要求学生认证，但不得拥有、复制或自行修改
   学生认证结果。
4. `DEC-004`：**Koishi 是 QQ 平台执行器**，负责接收 QQ 事件以及执行同意、禁言、提醒、解禁、拒绝、踢出
   等动作，不是学生身份真源。
5. `DEC-005`：**学校认证能力由配置和适配器驱动**，不得在前端硬编码“北航自动、外校人工”。外校当前默认
   只开放人工材料审核，但必须预留学校 SSO、学校邮箱和学籍名册等扩展方式。
6. `DEC-006`：**在线进程与 Oracle 完全隔离**。Web API、Admin、Koishi 及其他用户请求进程不得
   持有 Oracle 凭据、不得建立 Oracle 连接池、不得在请求链路访问 Oracle；只有隔离的校园连接器可在
   调度执行期间使用用户明确指定的既有账号短时登录并执行代码中固定的 `SELECT`。StuHelper 不得创建、
   申请、更换、授权、回收或修改该账号；在线认证只读取本地、版本化、可回滚的学籍快照。
7. `DEC-007`：**学生状态由有效认证凭据派生**，不得以一个不会随凭据过期或撤销而变化的永久布尔值作为
   权威依据。
8. `DEC-008`：**手机号验证不是学生身份证据，学生认证本身不得强制绑定手机号**。手机号属于
   StuHelper 账号的全局联系方式和附加认证凭据：规范化完整号码以 Casdoor 为唯一可写权威源；
   StuHelper PostgreSQL 可保存业务受权范围内可读的完整值投影、唯一性 HMAC 和带来源、时间及状态的
   手机号验证凭据，但投影只能由 Casdoor 变更流程同步，不得成为第二写真源。手机号不得单独或
   组合授予学生身份。
9. `DEC-009`：**内容发布前要求已验证手机号是 StuHelper 的产品风控门槛**。学生认证可以在未绑定手机号时完成；用户首次发帖或使用其他明确配置的发布能力前，
   再进入独立的手机号绑定流程。该门槛不得被混入学生凭据或学校认证适配器。
10. `DEC-010`：**用户侧自动证件方法统一称为“实名信息校验”**。北航目标实现直接使用
    本地学籍快照中的学号、姓名和身份证件安全投影做一致性校验。**学校教务系统提供的学籍记录属于
    必须严格保密的信息**：方法名、表单、普通错误和帮助文档不得暴露内部表名、字段、比对顺序或可用于
    枚举学生记录的细节。所有用户可见文案必须与真实处理路径一致：统一使用中性的“实名信息校验”，
    说明由 StuHelper 服务端完成信息一致性校验、本次填写原文不持久化；**未实际调用的腾讯云人脸核身、
    公安、政务或其他第三方实名服务不得出现在方法说明、隐私告知、客服话术或结果页中**。内部凭据
    元数据、审计和指标按 `DOC-007`、`SEC-006` 记录真实处理路径。本条不影响腾讯云短信作为
    `PHONE-008` 的 OTP 通道。
11. `DEC-011`：**校园内网连接是独立基础设施能力**。学校 SSO、LDAP、Oracle 和其他内网依赖通过
    受限校园连接器使用；学生认证、学籍同步和学校适配器不得各自建设任意网络隧道。
12. `DEC-012`：**旧学生认证数据不迁移、不备份、不兼容**。上线时一次性清除旧学生档案、旧认证
    凭据、旧实名记录、旧新生/人工材料和旧学籍本地表，所有用户均从新模型重新认证。不得为本次
    切换制作旧认证数据导出、备份表、映射表或兼容副本。该清理不得删除 StuHelper/Casdoor 用户账号、
    QQ 绑定、手机号及手机号凭据、群策略或普通业务数据。既有整库备份、物理基准备份和可恢复到
    清理前状态的 WAL 可能同时包含旧认证数据与非目标域数据；行级 migration 无法选择性擦除这些
    介质，必须按 `MIG-025` 在生产切换前单独处置，不能把在线库清零表述为“所有历史副本已清零”。

### 2.2 领域关系

```text
StuHelper 账号认证（Casdoor）
            │
            ▼
┌──────────────────────────────┐
│ 学生认证服务                 │
│                              │
│ 学校配置 → 验证方法适配器    │
│          → 本地学籍快照      │
│          → 人工审核          │
│          → 学生认证凭据      │
└──────────────┬───────────────┘
               │ 受控资格查询 / 领域事件
       ┌───────┴────────┐
       ▼                ▼
课程、资源等业务     群聊入群准入服务
                         │
                         ▼
                   Koishi / QQ 执行器

QQ 账号绑定 ──────────────┘
```

学生认证服务只关心“哪个 StuHelper 用户通过了哪所学校的哪种证明、有效到何时”。它不关心 QQ
群、QQ 入群会话、禁言或解禁。

群聊入群准入服务只关心“当前平台账号对应哪个 StuHelper 用户，以及该用户是否满足本群策略”。
其数据访问边界由 `CORE-008` 和 `ADM-002` 约束。

## 3. 目标与非目标

### 3.1 目标

- 为本校学生提供多种并列、可选择的自动认证方法；
- 为不适用自动认证的本校学生和外校学生提供安全的人工材料审核；
- 支持一个用户在本科、硕士、博士或跨校学习期间关联多段学籍；
- 允许群聊、课程、资源、开放平台等多个消费方复用同一份学生认证结果；
- 让不同学校通过配置逐步接入各自的 SSO、邮箱、名册或人工审核方式；
- 通过本地学籍快照隔离 Oracle，避免在线服务依赖学校数据库的持续可用性；
- 在身份过期、撤销、学籍变更和快照陈旧时及时收回学生资格；
- 提供移动优先、低认知负担、可恢复、无障碍的认证体验；

### 3.2 非目标

- `SCOPE-001`：不在“实名信息校验”的方法名称、卡片标题、字段说明或普通错误中展示“学籍证件号
  比对”、Oracle、表名、源字段或内部匹配顺序；
- `SCOPE-002`：不替代学校教务系统，不向学校数据库写入数据；
- `SCOPE-003`：不以 QQ 号、QQ 昵称、群名片或群管理员口头确认作为学生身份证明；
- `SCOPE-004`：不把学校 SSO 密码保存为 StuHelper 账号密码；
- `SCOPE-005`：不把学生、新生或群成员业务角色写入 Casdoor 作为授权真源；
- `SCOPE-006`：不为满足升学换学号而维护固定的“旧学号/新学号”两列；
- `SCOPE-007`：不新增一套与项目 PostgreSQL 身份账本并行的临时 MySQL 个人信息数据库；
- `SCOPE-008`：不承诺普通 Web 浏览器能够以密码学方式证明图片一定来自后置摄像头；
- `SCOPE-009`：不默认在学生凭据撤销后自动踢出现有群成员，持续成员治理由群策略另行决定。
- `SCOPE-010`：北航产品策略接受“规范学号、姓名和用户手工输入的手机号与当前学籍快照一致”作为
  可免短信的手机号校验方法；该方法证明用户输入与学校权威记录一致，产品可以据此认为“手机号已验证”。
- `SCOPE-011`：不把校园连接器建设为通用 VPN、代理、远程桌面或任意内网访问入口。

## 4. 术语

| 术语 | 定义 |
|------|------|
| StuHelper 账号认证 | 用户通过 Casdoor 登录 StuHelper，证明对本站账号的控制权 |
| 学校 SSO 验证 | 使用某所学校的统一身份认证作为学生证明方法，不等同于 StuHelper 自身登录 |
| 学校认证适配器 | 针对一所学校实现账号 subject、学号规范化、姓名匹配、邮箱派生和上游协议映射的受控组件 |
| 校园连接器 | 部署在经批准校园网络环境、只向外建立受认证连接并暴露有限学校数据操作的基础设施代理 |
| 学生认证 | 证明某个 StuHelper 用户当前具备某所学校学生身份的业务流程 |
| 学籍记录 | 某学校为一个学号提供的姓名、学籍状态和可用证明字段 |
| 学籍快照 | 从学校数据源定期同步、完整校验并在本地原子激活的只读学生名册版本 |
| 验证方法 | 实名信息校验、学校 SSO、学号邮箱、人工材料等一种证明手段 |
| 验证申请 | 用户为取得学生身份而发起的一次流程，可包含多次尝试或人工审核 |
| 认证凭据 | 某次验证成功形成的可审计事实，包含学校、方法、主体、状态和有效期 |
| 学生资格 | 根据当前有效凭据、学籍和消费方策略实时派生的结果 |
| 平台账号绑定 | StuHelper 用户与 QQ 等外部平台账号之间的一对一或受控映射 |
| 手机号验证凭据 | 证明某个 StuHelper 账号以特定方法核验过某号码的账号级事实，不等同于学生凭据 |
| 入群准入会话 | 某个平台账号针对某个群的一次入群处理流程 |
| 消费方 | 读取学生资格作业务决策的模块，例如群聊准入、课程、资源或开放平台 |

- `TERM-001`：用户文案必须区分“登录 StuHelper”和“使用学校统一身份认证验证”，避免把本站账号
  登录与学校身份核验混为一个 SSO 概念。

## 5. 参与者与职责

| 参与者 | 职责 |
|--------|------|
| 申请人 | 登录 StuHelper、选择学校和验证方法、提交证明或材料、查看结果 |
| 学生认证服务 | 编排验证方法、保存申请和凭据、派生学生资格、处理过期与撤销 |
| 学校适配器 | 提供某所学校的 SSO、邮箱、名册或其他证明能力 |
| 校园连接器 | 提供受限内网连接、节点身份、健康状态和传输审计，不判断用户是否为学生 |
| 学籍同步任务 | 短时读取学校数据源、校验快照、原子激活、记录审计和指标 |
| 人工审核员 | 在授权范围内查看必要材料并批准、驳回或要求补充 |
| 学校管理员 | 配置学校、可用方法、邮箱域、名册规则、审核策略和有效期 |
| 群管理员 | 配置群准入要求并处理群级异常，不直接授予学生身份 |
| 群聊准入服务 | 将平台绑定、学生资格和群策略组合为准入决定 |
| Koishi | 接收 QQ 事件、调用受控接口、幂等执行 QQ 动作并上报结果 |

## 6. 核心对象与不变量

### 6.1 对象关系

目标模型包含以下概念层面的对象；本文不固定具体表名：

- `User`：StuHelper 用户；
- `School`：学校及其认证能力配置；
- `EnrollmentSubject`：一个用户在一所学校的一段学籍，可拥有独立学号和有效期；
- `VerificationApplication`：一次学生认证申请；
- `VerificationAttempt`：一次证件号、OTP、SSO 或其他方法尝试；
- `VerificationCredential`：验证成功后形成的凭据；
- `PhoneVerificationCredential`：手机号的验证来源、保证等级、时间、状态和修订号；
- `ManualReview` / `Material`：人工审核决定和私有材料；
- `RosterSnapshot` / `RosterRecord`：版本化本地学籍快照；
- `PlatformIdentityBinding`：用户与 QQ 等平台账号的绑定；
- `AdmissionPolicy` / `AdmissionSession` / `AdmissionAction`：群聊准入策略、会话和执行动作。

### 6.2 强制不变量

- `CORE-001`：学生认证申请和凭据不得要求存在 QQ 绑定。
- `CORE-002`：学生认证申请和凭据不得保存 QQ 群号或 admission session ID 作为身份事实的一部分。
- `CORE-003`：同一用户可以持有多所学校、多段学籍和多个历史学号。
- `CORE-004`：学号是学校范围内的标识，不是跨学校全局主键。
- `CORE-005`：同一学校的同一当前学籍主体原则上只能绑定一个活动 StuHelper 用户；冲突必须
  进入账号找回或人工处置，不得静默抢占。
- `CORE-006`：姓名、手机号或邮箱相似不得单独触发两个 StuHelper 账号自动合并。
- `CORE-007`：升学产生新学号时新增学籍关系；不得覆盖历史学号，也不得依靠固定“学号（新）”字段。
- `CORE-008`：消费方只能通过学生资格查询契约或领域事件使用结果，不得跨模块直接读写认证表。
- `CORE-009`：认证凭据状态变化后，聚合学生资格必须可重算；过期或撤销不得留下永久
  `verified=true`。
- `CORE-010`：学校配置、认证结果、人工审核和群策略的权限边界必须通过 PostgreSQL 授权账本和
  capability 表达，不从普通 OIDC `roles` claim 派生。
- `CORE-011`：Casdoor 的 `Phone` 字段是账号当前号码的唯一可写权威源；StuHelper 号码投影只供受权业务读取，
  个人中心、管理员和后台任务都不得绕过 Casdoor 直接修改、解绑或覆盖投影。没有可验证的手机号凭据时，
  不得仅因 `Phone` 非空就满足内容发布门槛。
- `CORE-012`：学校记录实名信息一致性结果、学生主体关联结果和最终学生凭据是三个可审计但相互独立的
  事实；任一消费方不得把其中一个永久布尔值当作其他两个事实的替代品。

## 7. 学生认证入口与通用流程

### 7.1 独立入口

- `SV-001`：学生认证必须有与 QQ、群聊和 admission token 无关的主站入口。
- `SV-002`：用户必须先登录 StuHelper，认证结果绑定当前内部用户 ID。
- `SV-003`：入口可以由账号中心、群聊准入或其他消费方打开，但学生认证业务结果保持一致。
- `SV-004`：消费方发起时可以携带短期、签名的继续流程凭据；该凭据只用于安全返回消费方，
  不得改变学生认证判定。
- `SV-005`：继续地址必须来自服务端白名单或注册的消费方，不接受任意 `redirect` URL。
- `SV-006`：完成认证后，消费方必须重新查询资格；不得只相信浏览器 query、前端状态或回跳参数。

### 7.2 通用步骤

```text
登录 StuHelper
    ↓
选择学校
    ↓
读取学校当前可用验证方法
    ↓
选择一种方法并完成证明
    ↓
自动通过 / 等待人工审核 / 失败后切换方法
    ↓
形成认证凭据并展示有效期
```

- `SV-010`：前端必须以服务端返回的学校能力为准显示方法。
- `SV-011`：每种方法只收集完成该方法所需的字段，不预先展示全部字段。
- `SV-012`：同一次申请可在策略允许时切换验证方法，但不同方法的尝试次数和证据必须独立审计。
- `SV-013`：自动方法失败不得自动创建缺少必需材料的人工审核申请。
- `SV-014`：失败响应不得帮助攻击者枚举学号、姓名、身份证件号、邮箱或账号是否存在。
- `SV-015`：用户必须能查看当前状态、验证方法、学校、通过时间、有效期及可执行的下一步。

## 8. 学校能力配置

### 8.1 能力注册表

每所学校可以独立配置以下方法：

| 能力标识 | 用户含义 |
|----------|----------|
| `real_name_identity_check` | 使用姓名和身份证件号完成实名信息校验 |
| `school_sso` | 使用学校统一身份认证验证 |
| `student_email_outbound_otp` | 系统向规范学号邮箱发送验证码 |
| `student_email_inbound_challenge` | 用户从规范学号邮箱发送验证邮件 |
| `manual_material_review` | 提交学校和学生材料，由人工审核 |

- `SCH-001`：方法列表必须来自后端学校配置和适配器健康状态，不得由学校名称的前端条件分支决定。
- `SCH-002`：接收邮箱验证码和发送验证邮件是两个独立开关，可同时开启、单独开启或全部关闭。
- `SCH-003`：学校配置必须支持方法文案、邮箱域、学校适配器、学号规范化、姓名匹配、名册新鲜度、
  凭据有效期、人工表单、风险限制，以及每种方法的名册依赖策略。
- `SCH-004`：适配器不可用时只关闭受影响的方法；其他健康方法仍可选择。
- `SCH-005`：学校新增 SSO 或名册适配时不得要求改动通用前端流程。
- `SCH-006`：学校方法配置变更必须审计，并支持先验证配置再启用。
- `SCH-007`：学校目录只用于代码、名称和搜索展示，不构成认证白名单。只有存在已启用、校验通过的
  学校认证配置，并且至少有一个健康方法时，该学校才能创建认证申请；“新增学校建议”不得自动启用
  学校认证。

`SCH-008`：每种方法的 `roster_dependency` 必须取以下值之一：

| 值 | 含义 |
|----|------|
| `required` | 凭据形成时必须命中当前有效名册并满足学生准入规则 |
| `independent` | 该方法按自身证据形成凭据，不依赖本地名册 |
| `conditional` | 只有上游证据不能可靠证明学生属性时才追加名册门槛 |

- `SCH-009`：`conditional` 方法必须配置可执行的判定条件，不能把“上游看起来可信”作为人工判断。
- `SCH-010`：方法的名册依赖策略变更可能改变既有资格，发布前必须计算影响范围、审计并触发受控重评估。

### 8.2 北航目标配置

北航当前目标方法为：

1. 实名信息校验；
2. 北航统一身份认证；
3. `学号@buaa.edu.cn` 接收验证码；
4. 从 `学号@buaa.edu.cn` 发送验证邮件；
5. 自动方法不可用时的人工审核兜底。

- `SCH-011`：邮箱域必须由学校配置保存；除配置 bootstrap 和适配器契约测试外，界面、通用服务层和
  消费方不得散落学校域名硬编码。

北航推荐初始名册依赖配置为：

| 方法 | `roster_dependency` | 说明 |
|------|---------------------|------|
| `real_name_identity_check` | `required` | 使用当前名册中的学号、姓名和证件安全投影完成一致性校验 |
| `student_email_outbound_otp` | `required` | 邮箱必须由当前名册中的规范学号派生 |
| `student_email_inbound_challenge` | `required` | 发件邮箱必须对应当前名册中的规范学号 |
| `school_sso` | `conditional` | 上游能证明学生属性时独立通过，否则追加当前名册匹配 |
| `manual_material_review` | `independent` | 依靠人工材料决定，但必须设置有效期或复核时间 |

### 8.3 学校适配器契约

学校差异不得沉淀为通用 Service 或前端里的学校名称条件分支。每所学校的适配器按启用能力实现下列
契约；底层可以复用 LDAP、CAS、OIDC、SAML、邮件等协议驱动，但协议驱动不得替代学校适配器：

| 契约 | 职责 |
|------|------|
| `normalize_student_id` | 去除允许的格式差异并产生唯一规范学号，不擅自截断或猜测 |
| `validate_student_id` | 按学校规则校验长度、字符、校验位或其他结构 |
| `normalize_and_match_name` | 按学校批准规则处理空白、字符和姓名一致性 |
| `derive_canonical_student_email` | 从已经验证的规范学号派生唯一学校邮箱 |
| `authenticate_school_account` | 调用该校受支持的 SSO/LDAP 等上游并返回稳定学校 subject |
| `map_roster_record` | 将学校字段映射为通用名册记录并保留映射版本 |
| `evaluate_enrollment` | 按学校批准的状态和时间规则判断当前学生资格 |

- `SCH-012`：学号规范化和格式校验必须按学校选择适配器策略。简单学校可以使用受长度限制的
  RE2 兼容正则和声明式大小写规则；复杂学校使用经过测试的代码适配器。不得执行管理员提交的任意
  JavaScript、SQL、模板表达式或其他脚本。
- `SCH-013`：通用服务不得先使用一个全局学号正则拒绝请求，再调用学校适配器；长度和 Unicode
  安全上限可以全局统一，学号构成规则必须由学校决定。
- `SCH-014`：北航学号先由当前有效本地快照中的“学号 + 姓名”匹配确认；匹配后的快照学号就是
  规范学号，北航邮箱由该值与配置域 `buaa.edu.cn` 派生，不再对用户开放邮箱本地部分编辑。
- `SCH-015`：人工审核使用同一个受控表单引擎和拍摄组件；学校只配置字段 schema、选项、文案、
  材料类型和审核策略。学校 SSO 必须单独选择学校适配器，不得复用另一个学校的登录流程。
- `SCH-016`：学校适配器输出必须包含适配器 ID、版本、学校 subject、使用的上游协议、名册依赖结果
  和稳定错误类别；用户密码、服务账号秘密和上游原始响应不得进入输出或持久化证据。
- `SCH-017`：新增或升级适配器必须通过学校契约样例、错误映射、安全测试和灰度健康检查后才能
  启用；通用前端只消费能力描述和字段 schema，不感知适配器实现类。

### 8.4 校园内网连接平面

```text
StuHelper 生产服务 ── mTLS / 受控消息契约 ── 校园连接器 ── 学校 LDAP / Oracle
        │                                      │
        └── 不获得通用校园网路由               └── 只允许已登记目标、端口和操作
```

- `NET-001`：校园连接器是独立基础设施模块，只提供受控连接、节点身份、健康检查、限流、审计和证书
  轮换；它不得判断学生资格、创建学生凭据或保存 admission 会话。
- `NET-002`：连接器必须部署在学校批准、稳定、可运维的校园网络节点，并由该节点主动建立出站的
  双向认证连接；个人开发机、临时笔记本、家用远程桌面或开发者交互会话不得成为生产网关。
- `NET-003`：生产端只可调用登记过的高层操作，例如“校验一次学校账号”或“上传一个签名快照”；
  不得暴露通用 TCP 转发、SOCKS、HTTP 代理、Shell、任意 URL 或任意 SQL 接口。
- `NET-004`：连接器同时实施节点身份、服务身份、学校、目标主机、端口和操作级 allowlist；采用三层
  组网时还必须用精确路由和防火墙限制到批准目标，不能把整个校园网段路由给生产环境。
- `NET-005`：学校服务账号、用户明确指定的既有 Oracle 账号和 TLS 私钥必须来自连接器所在环境的 secret reference，
  不写学校配置 JSON、管理后台响应、数据库普通配置列或代码仓库；用户输入的学校密码不得与服务
  账号秘密复用。
- `NET-006`：学校密码只允许在一次同步请求的加密传输和受控内存中存在。请求取消、超时、连接器
  离线或队列拥塞时必须销毁，不得落盘、进入 Redis、消息持久化、重试队列、日志、Trace 或崩溃转储。
- `NET-007`：学籍同步优先由校园连接器在校园侧短时读取 Oracle，生成带 schema 版本、源截止点、
  行数、校验和和签名的加密快照后主动推送；生产端只接收、验证和激活快照，不获得 Oracle 网络权限。
- `NET-008`：连接器必须支持节点吊销、单节点并发上限、熔断、版本兼容、证书轮换、心跳和审计；
  身份不明、版本不兼容、签名错误或健康状态未知时相关学校方法 fail closed，不影响其他学校和方法。
- `NET-009`：连接器只返回完成业务所需的最小结果和稳定错误分类；LDAP 属性全集、Oracle 行原文、
  服务端堆栈和内网拓扑不得返回浏览器或 Koishi。
- `NET-010`：是否采用 WireGuard 等三层组网、应用层反向连接或两者组合属于实施设计；无论选择哪种
  技术，都必须满足 `NET-001`—`NET-009`，不得让网络便利性扩大业务授权范围。
- `NET-011`：Oracle 默认使用经过 CA 和证书名验证的 TCPS。既有学校接线只能通过审核过的 SSH 跳板
  访问 1521 时，允许由校园节点运维层建立固定 SSH local forward；连接器只能拨号到一个 loopback
  高端口，不能管理 SSH 私钥、执行 SSH、接受 listener redirect 或把该例外表示成通用 TCP 转发。
- `NET-012`：SSH 跳板 host key、私钥、远端 Oracle 地址和端口必须固定在校园节点 secret/运维配置；
  禁止 `GatewayPorts`、动态转发和 SOCKS。该模式不等于 Oracle 原生 TCPS，学校提供 TCPS 后必须迁回
  默认模式。

## 9. 北航实名信息校验

本节定义用户可见的“实名信息校验”方法。北航目标实现不调用外部二要素 provider，而是在受控后端内
将用户提交的学号、姓名和身份证件号与当前本地学籍快照做安全一致性校验。学校学籍数据源属于必须严格
保密的信息：方法卡片、表单、错误提示和帮助文档不得展示内部数据源、表名、字段或匹配顺序；全部用户
可见文案按 `DEC-010` 和 `DOC-011` 使用真实、最小披露的中性表述，隐私说明准确披露实际处理活动。

### 9.1 用户输入和判定

- `DOC-001`：该方法要求用户输入规范学号、姓名和完整中国大陆居民身份证件号；QQ 号和手机号不是
  本方法字段。
- `DOC-002`：北航适配器必须先确认规范学号与姓名匹配当前有效本地快照；失败只返回不可枚举的通用
  结果，不说明学号、姓名或当前学生状态中的哪一项不一致。
- `DOC-003`：只有学校源记录的证件类型支持大陆居民身份证，且存在有效安全比对值时，才能继续本方法。
- `DOC-004`：用户提交的身份证件号必须在服务端通过长度、字符、出生日期和校验码检查；客户端校验
  只用于即时反馈，不能替代服务端校验。
- `DOC-005`：源证件号为空、格式无效或没有安全比对值时，本方法必须不可用，但用户仍可选择学校
  统一身份认证、学校邮箱或人工审核。
- `DOC-006`：用户提交的证件号必须在受控内存中规范化并计算带版本密钥的 HMAC，再与当前快照的
  安全投影执行常量时间比较；不得为比较目的批量解密学校源证件号。
- `DOC-007`：北航方法的实际核验证据就是当前快照中的学号、规范化姓名、当前学生状态和证件号
  带密钥 HMAC 安全投影；实现不调用腾讯云或其他外部实名 provider。内部凭据元数据和审计必须记录
  真实处理路径，不得伪造 provider 请求 ID、响应体或第三方调用日志；用户可见文案同样不得暗示或
  声明发生了不存在的第三方调用。
- `DOC-008`：只有规范学号、姓名、当前学生状态和证件安全投影全部一致，且凭据形成事务内对当前
  active snapshot revision 最终复查通过时，才形成 `real_name_identity_check` 学生凭据。
- `DOC-009`：学号、姓名、证件号、当前学生状态不一致和主体冲突，必须对普通用户归并为不可枚举的
  稳定失败类别；快照过期、密钥不可用或本地依赖故障必须归为依赖不可用，不能伪装成用户信息错误。
- `DOC-010`：不同本地匹配失败路径应避免可被批量利用的明显响应长度和时长差；限流、退避和统一人工核查
  入口适用 `ABUSE-001`—`ABUSE-004`。

### 9.2 产品文案与告知

- `DOC-011`：方法卡片和页面标题必须统一称为“实名信息校验”，不得出现“学籍核验”“证件号与学籍
  比对”、Oracle、源表或内部字段名称。方法说明必须真实、简明地说明“由 StuHelper 服务端校验您提交的
  学号、姓名和证件信息是否一致；本次填写的姓名和证件号原文不持久化”，不得声称调用未实际使用的
  第三方实名服务。该要求覆盖方法卡片、表单说明、结果页、普通错误提示和帮助文档。
- `DOC-012`：普通错误和帮助文档不得暴露可用于枚举学生记录的内部细节，包括 Oracle owner、表名、
  字段、快照主键或逐字段匹配结果；依赖不可用时使用 `UX-ERR-001` 的通用降级文案。隐私说明仍必须
  按真实处理活动履行法定告知，不得用“保密”为由虚构处理者或接收方。
- `DOC-013`：任何前端界面、提示、客服话术和帮助文档不得使用“腾讯云人脸核身”“公安实名”“政务
  核验”或其他第三方背书，除非该 provider 已真实接入、完成授权与隐私评审，并能提供真实请求审计。
- `DOC-014`：内部方法枚举固定为 `real_name_identity_check`，审计、指标、错误分类和凭据元数据一律
  使用内部真实值；用户可见文案从经审查的产品文案注册表取得，不得直接泄漏内部方法或数据结构。
- `DOC-015`：隐私说明必须准确描述 StuHelper 自行完成服务端一致性校验，并完整列明处理目的、数据
  种类、保存期限、是否向第三方共享、用户权利入口及真实的数据处理边界。隐私说明版本必须与
  `DOC-016` 的同意记录关联。
- `DOC-016`：首次提交前必须取得与当前隐私说明版本关联的明确同意；处理敏感个人信息所需的单独同意、个人信息保护影响评估和内部访问控制必须在生产启用前完成；未来真实增加第三方 provider 时，再另行完成告知、同意和委托处理要求。

### 9.3 敏感数据与持久化边界

- `DOC-017`：用户在本方法中本次填写的身份证件号原文，只存在于浏览器当前表单、单次 HTTPS 请求
  受控内存和本地安全比对所需的最短生命周期；不得写入 PostgreSQL、Redis、Session、对象存储、队列、
  临时文件、日志、Trace、指标 label、错误报告、客服工单、前端埋点或会话回放。本次提交的姓名不单独
  持久化为“用户提交证据”；姓名的权威副本按 `SNAP-041` 保存在快照侧，两者不得混用或互相回填。
- `DOC-018`：学生快照按 `SNAP-041` 保存学校提供的姓名、证件号密文与 HMAC，但它们必须与用户本次
  表单值和实名凭据分层；凭据只保存方法、结果类别、通过时间、快照 revision、适配器版本和有效期，
  不保存伪造的 provider 字段或外部请求 ID。
- `DOC-019`：不得把本次姓名或身份证号写入 Casdoor 的 `RealName`、`IdCard` 或其他用户属性来换取
  `IsVerified`，否则不满足本节“不保存本次提交原文”的目标；账号登录身份和实名学生凭据保持解耦。
- `DOC-020`：服务端不得向前端返回学校源证件号、尾号、出生日期、安全投影、内部记录定位标识
  或格式错误细节；用户侧只接收稳定状态、通用文案和可执行的下一步。
- `DOC-021`：快照证件号 HMAC 必须使用服务端秘密密钥并记录密钥版本，普通无密钥 SHA-256 不构成
  安全保护；密钥轮换必须支持受控双读和重新投影。重新投影优先使用下一次完整同步的源值；确需从现有
  密文重算时，必须作为一次受审批、有界、全程审计的批处理执行，不得成为常规读路径。
- `DOC-022`：学校源证件号按 `SNAP-041` 保存可逆密文与 HMAC，由同一受控同步路径从同一源值原子
  生成。该授权只覆盖学校源值，不授权保存用户在本方法中提交的证件号原文。

## 10. 学校统一身份认证

### 10.1 业务规则

- `SSO-001`：用户从 StuHelper 选择学校统一身份认证方法后，系统发起学校对应适配器流程。
- `SSO-002`：成功结果必须包含稳定、受验证的学校账户 subject；不得以浏览器提交的学号作为
  SSO 成功主体。
- `SSO-003`：同一次流程必须使用 `state`、nonce、PKCE 或等价的防串改和防重放机制。
- `SSO-004`：学校返回的账户必须与最终绑定的学籍主体一致，冲突时不得覆盖已有绑定。
- `SSO-005`：如果学校登录入口或返回属性不能可靠区分学生与教职工，必须将返回账号与当前有效
  学籍快照匹配；只有已由学校契约保证“该入口仅面向学生”时，才可配置为登录成功即通过。
- `SSO-006`：验证成功形成 `school_sso` 凭据，其有效期和重新认证周期由学校配置决定。

北航产品目标是“北航统一身份认证账号校验成功，并且账号状态与学生主体规则满足时完成该证明
方式”。北航 LDAP 目录是否可靠限定学生主体属于 `GATE-001` 的上线确认项；不能可靠限定时适用
`SSO-005` 的名册门槛。

### 10.2 接入优先级

学校 SSO 按以下优先级接入：

1. `SSO-007`：优先使用学校官方提供的 OIDC、CAS、SAML 或其他浏览器跳转协议。
2. `SSO-008`：官方浏览器协议不可用时，只能使用学校明确授权的服务端认证代理或学校目录协议，
   例如 LDAP user bind。
3. `SSO-009`：只有确认不存在可用官方方案、取得系统所有方授权，并完成安全、合规和凭据处理评审
   后，才能启用表单模拟登录适配器。

### 10.3 表单式学校账号验证约束

如果学校只能接收用户在 StuHelper 表单输入的学校账号和密码，再由服务端或校园连接器完成验证：

- `SSO-010`：必须取得学校或系统所有方的明确授权，不绕过验证码、MFA、风控或访问限制。
- `SSO-011`：学校密码只存在于单个请求的受控内存，不写数据库、Redis、Session、队列或对象存储。
- `SSO-012`：密码不得写入日志、Trace、错误堆栈、前端分析平台或客服工单。
- `SSO-013`：必须校验学校服务端 TLS 证书，不允许关闭证书验证。
- `SSO-014`：必须限制并发、频率和失败次数，并为学校服务设置超时、熔断和退避。
- `SSO-015`：学校登录页面、LDAP schema、字段、验证码或响应结构发生未知变化时必须停止该方法并
  告警，不得猜测成功。
- `SSO-016`：方法名称只称“统一身份认证验证”；如实现确实由 StuHelper 代为提交
  一次学校凭据，提交前说明可以使用“模拟登录您的学校 SSO 账号进行校验”的准确措辞，
  但不得使用“代登录”、暗示会保存密码，或引导用户把学校密码交给管理员。

### 10.4 北航 LDAP 适配器

- `SSO-017`：北航目标适配器使用独立标识 `buaa_ldap_bind`。通用学生认证服务只调用学校适配器，
  不拼接北航 DN、LDAP filter、属性名或内网地址；其他学校必须选择各自适配器。
- `SSO-018`：适配器先使用用户提交的规范学号构造受控 user DN，执行一次 user bind 验证密码；DN
  模板只能来自受审配置，学号必须先经过北航适配器规范化和 LDAP DN 转义，浏览器不得提交完整 DN
  或任意 filter。
- `SSO-019`：user bind 成功后，适配器可以使用独立的最小权限查询身份读取账号状态和批准属性；
  查询必须限定规范学号，并确认账号未锁定、未禁用。服务账号不得代替 user bind，也不得用于尝试
  用户密码。
- `SSO-020`：系统查询账号必须使用 secret reference；连接地址、Base DN、受控 DN/filter 模板和属性
  映射可以进入非秘密配置，服务账号口令不得进入 `school_configs.ldap_config`、管理后台表单回显、
  普通数据库配置、日志、代码、文档或聊天记录。
- `SSO-021`：LDAP user bind、系统 bind 和查询必须使用校验证书的 LDAPS 或 StartTLS。仅依赖校园
  隧道不能把明文 `ldap://` user bind 自动提升为安全传输；上游无法提供受验证 TLS 时，该方法不得
  生产启用，除非安全 owner 批准了独立的同网段 TLS 终止代理和有界例外。
- `SSO-022`：生产环境通过 `NET-001`—`NET-010` 的校园连接器执行北航 LDAP 操作；连接器不可用时
  只关闭北航统一身份认证方法，实名信息校验、邮箱和人工审核按各自依赖状态继续工作。
- `SSO-023`：用户侧在提交按钮前显示以下等价文案：

> 本功能会使用您输入的账号和密码，模拟登录您的北航统一身份认证账号进行一次性校验。
> StuHelper 不存储您的统一身份认证密码。

- `SSO-024`：密码输入框必须使用当前请求内存提交，不启用浏览器持久化、前端分析和会话回放；
  页面刷新、失败重试和连接器重连都必须要求用户重新输入密码。
- `SSO-025`：LDAP 查询返回的手机号只可作为学校来源候选值；LDAP 登录成功、属性非空或学生认证成功都不得
  自动绑定、自动填入或写入 Casdoor。只有用户在手机号流程中当次手工输入号码，并满足 `PHONE-006`—`PHONE-008`
  后才可形成手机号凭据。
- `SSO-026`：适配器必须区分凭据错误、账号锁定或禁用、主体不属于学生、连接器不可用、TLS 失败、
  上游超时和配置漂移等内部类别；普通用户只看到不可枚举的凭据失败或服务暂不可用，安全审计保留
  不含账号和密码的分类。

## 11. 规范学号邮箱验证

### 11.1 共同规则

- `MAIL-001`：用户选择学校后输入学号和姓名；学校适配器规范化后，两者必须匹配当前有效本地快照。
- `MAIL-002`：邮箱必须由学校适配器按已经匹配成功的规范学号和学校配置域名派生，客户端不得提交
  替代邮箱或自行修改本地部分。
- `MAIL-003`：北航默认邮箱为 `规范化学号@buaa.edu.cn`。
- `MAIL-004`：邮箱本地部分必须精确等于学籍快照中的规范学号，不接受别名、昵称、任意前缀或
  仅凭域名匹配。
- `MAIL-005`：同域名的教职工、校友或其他邮箱，如果本地部分不在当前准入名册中，不得通过。
- `MAIL-006`：界面只展示必要的脱敏地址。

### 11.2 系统向学校邮箱发送验证码

- `MAIL-010`：系统向服务端派生的规范学号邮箱发送一次性验证码。
- `MAIL-011`：验证码必须短期有效、一次性消费、服务端安全存储并限制错误尝试次数。
- `MAIL-012`：发送需按用户、学号、学校、目标邮箱哈希、IP 和设备风险进行冷却与限流。
- `MAIL-013`：发送服务压力过大或不可用时必须明确显示“该方式暂时不可用”，并允许选择其他方法。
- `MAIL-014`：邮件投递成功只表示服务商接受投递，不等于用户已验证；只有正确回填验证码才通过。
- `MAIL-015`：验证成功形成 `student_email_outbound_otp` 凭据。

推荐初始配置为验证码 10 分钟有效、60 秒发送冷却、最多 5 次回填尝试；生产启用条件见
`MAIL-016`。

- `MAIL-016`：验证码有效期、发送冷却和回填尝试上限必须配置化，并通过生产规模容量与滥用测试后
  才能作为生产值启用。

### 11.3 用户从学校邮箱发送验证邮件

- `MAIL-020`：服务端生成不可预测、短期、一次性的入站邮件挑战。
- `MAIL-021`：页面展示受控收件地址、邮件主题或正文挑战值，以及明确的有效期。
- `MAIL-022`：用户必须从精确的规范学号邮箱发送，别名地址不得通过。
- `MAIL-023`：入站处理必须校验可信邮件服务商签名、信封发件人、`From`、挑战值、TTL 和重放状态。
- `MAIL-024`：应检查 SPF、DKIM、DMARC 或学校邮件系统能提供的等价可信结果；不得只相信邮件正文
  或未经验证的 `From` 文本。
- `MAIL-025`：同一挑战只能完成一次申请，迟到、重复或转发邮件不得重复生效。
- `MAIL-026`：验证成功形成 `student_email_inbound_challenge` 凭据。
- `MAIL-027`：前端应通过短轮询、SSE 或等价机制更新结果，并为用户提供“尚未收到”“重新生成”
  和“改用接收验证码”的恢复路径。

## 12. 人工材料审核

### 12.1 适用范围

- `MAN-001`：外校学生当前只能通过人工材料审核形成学生凭据。
- `MAN-002`：外校邮箱验证、格式检查或学校域名匹配只能作为辅助证据，不得在当前阶段自动批准。
- `MAN-003`：北航留学生、非大陆证件持有人、学籍数据缺失者、自动方法全部不可用者可以使用人工兜底。
- `MAN-004`：录取通知书证明的是新生或待入学身份，不得伪装为无期限正式在校学生身份。

### 12.2 学校与表单

`FORM-001`：人工审核表单至少包含：

- 学校：从已启用人工审核能力的学校认证配置中搜索选择；
- 学院或院系；
- 学号或录取编号；
- 姓名；
- 学校邮箱或联系邮箱；
- 材料类型；
- 实际拍摄的校园卡、学生证、录取通知书或学校批准的其他材料。

规则如下：

- `MAN-010`：用户不得用自由文本替代已有学校；找不到学校时提交“新增学校建议”，不能即时创建
  可认证学校。
- `MAN-011`：学校配置了邮箱域时，界面应提供允许的后缀并校验；邮箱验证成功仍不跳过人工审核。
- `MAN-012`：学校没有可靠邮箱域时可以保留联系邮箱，但必须明确显示“未作为学校身份证明”。
- `MAN-013`：手机号不得作为学生身份证据，人工审核表单也不得为取得学生凭据而强制收集手机号。
  内容发布等账号级门槛按 `DEC-008`、`DEC-009` 和 `PHONE-001`—`PHONE-016` 在独立流程执行。
- `MAN-014`：字段由学校配置扩展时必须使用受控字段类型、长度和文案，不能执行任意脚本或 SQL。

### 12.3 材料拍摄

- `MAN-020`：产品界面只提供实时摄像头拍摄，不提供相册、普通文件选择、拖拽上传或 PDF 上传入口。
- `MAN-021`：浏览器具备本机拍摄能力时，应在解释用途后由用户主动触发摄像头权限，并优先请求
  `environment` 摄像头；不得仅凭 UA、触屏状态或视口宽度判定设备类型和安全能力。
- `MAN-022`：二维码交接必须作为可用的替代路径。本机没有可用摄像头、无法满足拍摄要求或权限被
  拒绝时，二维码是主要路径；本机可拍摄时，二维码与本机拍摄可以并存，视口只决定布局主次。
- `MAN-023`：手机拍摄会话必须短期有效、绑定原申请、一次性使用，并防止另一个申请复用。
- `MAN-024`：手机完成上传后，用户可以选择继续在手机完成或回到 PC；两端状态必须由服务端锁定，
  防止重复提交和结果分叉。
- `MAN-025`：后端必须验证实际文件类型、解码结果、大小和像素边界，不信任扩展名或浏览器
  `Content-Type`。
- `MAN-026`：材料存入私有对象存储，列表接口不得返回对象 key 或长期公开 URL。
- `MAN-027`：检测到 `getUserMedia` 只证明浏览器具备摄像头 API，不证明存在后置摄像头；系统不得
  因 `facingMode: environment` 请求成功就记录或展示“已证明使用后置摄像头”。

`MAN-028`：普通 Web API 无法可靠证明字节一定来自后置摄像头。验收只保证产品没有文件选择入口、
优先请求后置摄像头并通过受控拍摄会话上传；如果业务要求防篡改设备证明，必须另行建设原生应用和
设备证明。

### 12.4 审核结果

- `REV-001`：校园卡或学生证等当前学生材料，可以形成有明确复核周期的
  `manual_material_review` 学生凭据。
- `REV-002`：录取通知书形成临时新生凭据，必须设置 `expires_at`。
- `REV-003`：所有人工凭据都必须有到期或复核时间，不得永久有效。
- `REV-004`：驳回必须区分用户可见原因和内部风险备注。
- `REV-005`：材料不足时可以要求补充，但必须记录每次补充和审核历史。
- `REV-006`：审核员不得审核自己的申请。

## 13. 本地学籍快照

### 13.1 运行边界

- `SNAP-001`：Web API、Admin 和 Koishi 不得持有 Oracle 凭据或建立 Oracle 连接池。
- `SNAP-002`：只有隔离的学籍同步任务可以使用用户明确指定的既有 Oracle 账号访问学校数据源；无论
  该账号实际 grants 如何，客户端都只能执行仓库固定的 `SELECT`，不得为本项目创建或调整账号权限。
- `SNAP-003`：同步任务只在执行期间建立连接，完成或失败后立即释放。
- `SNAP-004`：在线学生认证只读取 PostgreSQL 当前激活的本地快照。
- `SNAP-005`：优先由 `NET-001`—`NET-010` 的校园连接器在学校网络内生成安全快照并主动推送；
  无法部署连接器且生产网络已经获得学校批准的最小路由时，才允许隔离的 StuHelper 同步 Worker
  定时短连接 Oracle。两种路径都不得进入在线请求进程。

### 13.2 数据范围

`SNAP-006`：北航同步只读取完成业务所需的字段：

- 学号 `XH`；
- 姓名 `XM`；
- 证件类型；
- 身份证件号 `SFZJH`；
- 学校登记手机号 `SJH`，作为北航已批准的手机号一致性校验源读取，并记录来源时间；
- 判断当前学生资格所需的学籍状态、是否在校、是否注册、培养层次和学生类别；
- 入学年级 `RXNJ`，或语义更明确的学籍 `valid_from` / `valid_until`；
- 数据源更新时间或快照时间。

- `SNAP-041`：学号、姓名、身份证件号和学校登记手机号在快照中以**可逆密文 + 确定性带密钥 HMAC
  盲索引**成对保存：密文供受权路径还原原值，HMAC 供等值查找和一致性比较。两侧必须由同一受控同步
  路径从同一源值原子生成，并记录加密密钥版本和 HMAC 密钥版本。学籍状态、培养层次、入学年级、
  证件类型等非直接身份字段可以明文保存。学号邮箱派生等确需明文的服务端逻辑按 `AUTHZ-007` 单行
  解密，不得为此保留额外明文列。
- `SNAP-042`：快照是这些身份字段的**唯一权威可逆数据源**。凭据、投影、消费方响应和下游业务表只
  保存不可逆值（HMAC 或脱敏展示值）即可，不得复制可逆密文；需要明文时一律回到快照按 `AUTHZ-007`
  受权解密。密文和密钥不得进入备份以外的任何导出物、开发环境或非生产副本。

- `SNAP-007`：不得因为“以后可能用到”同步地址、家庭信息、父母信息、财务信息、成绩或其他无关字段。
- `SNAP-008`：用于判断“当前学籍”的时间、状态和培养层次字段必须具有学校确认的代码语义，
  不能仅按原始字符串大小或数据库返回顺序选择活动学号。
- `SNAP-009`：源数据缺少可确定当前学籍的时间或状态证据时，可以保存历史学籍记录，但不得自动
  将其中任意一条标记为当前活动学籍。

### 13.3 版本化与原子激活

- `SNAP-010`：每次同步必须生成独立快照版本，记录学校、来源、源时间、开始/完成时间、行数、
  校验和、结构版本和状态。
- `SNAP-011`：新数据先写入暂存版本，全部校验通过后在单个事务中切换为当前版本。
- `SNAP-012`：失败或未完成的快照不得被在线查询读取。
- `SNAP-013`：新完整快照中不存在的记录必须从当前查询结果消失；仅做 upsert、保留历史遗漏行
  不满足要求。
- `SNAP-014`：同步失败时保留上一份成功快照，不得部分覆盖。
- `SNAP-015`：至少保留有限数量的成功历史版本用于回滚，并按隐私保留策略清理旧版本。
- `SNAP-016`：同步必须幂等，同一源版本重复导入不能产生重复学籍或重复凭据。
- `SNAP-017`：现有 `infra/ops/import-buaa-academic-students.sh` 是 upsert-only 导入器，不具备
  完整集合删除、快照版本或原子激活语义，不满足 `SNAP-010`—`SNAP-016`。在完成这些语义前，
  不得把它原样接入周期调度或作为权威快照激活路径；实现可以替换该脚本，也可以对其深度重构。
- `SNAP-018`：目标结构对学号、姓名、身份证件号和手机号一律保留可逆密文与 HMAC 成对存储，与现有
  `chk_buaa_students_sfzjh_secure_pair` 的“同生共死”语义一致；新增字段必须建立等价的成对 CHECK
  约束和密钥版本列。不得只写入其中一侧，不得填充无法解密的伪密文，也不得绕过数据库约束。
- `SNAP-019`：旧 upsert 表不得作为兼容读源、回退读源或影子读源；必须按 `DEC-012`、`MIG-003`
  在切换时清空。上线后名册查询只接受版本化快照的单一 active pointer；尚无活动快照时依赖名册的
  方法 fail closed，不得回读旧表。

### 13.4 数据质量门禁

激活前质量门禁包括：

- `QG-001`：学号和姓名必填及规范化结果有效。
- `QG-002`：学号在学校和快照范围内唯一。
- `QG-003`：同一学号不存在冲突姓名或相互矛盾的当前状态。
- `QG-004`：证件类型、证件格式有效；`SNAP-041` 要求的密文与 HMAC 成对存在、密钥版本可识别、
  密文可解密且 HMAC 可复算。
- `QG-005`：所有学籍状态代码均在学校批准的映射中。
- `QG-006`：总行数和准入人数相对上一版本没有超过配置化异常阈值。
- `QG-007`：源时间不早于当前版本；确需回退源数据时必须人工授权并审计。
- `QG-008`：规范化结果的校验和可复算且与导入作业记录一致。
- `QG-009`：激活前健康查询只输出聚合或匿名结果，不输出学生明细。
- `QG-010`：未知状态代码、行数大幅突变、重复学号或安全字段生成失败时必须中止自动激活并
  告警，不得使用默认“在校”状态猜测。

### 13.5 新鲜度与故障策略

- `SNAP-020`：同步周期、告警阈值和硬失效阈值必须按学校配置。
- `SNAP-020A`：学校可以显式启用完整快照自动激活，默认必须关闭。开启后只有签名、结构、隐私字段、
  来源时间和全部质量门禁均通过的 `ready` 快照可由系统原子激活；系统审计使用真实 `system` actor，
  不得伪造管理员用户。未开启、失败、来源回退或状态不确定时保持待人工处理。
- `SNAP-020B`：默认完整同步周期为 7 天、告警阈值为 8 天、硬失效阈值为 14 天；三者仍按学校可配。
  周期任务失败后使用 15 分钟起步、最长 6 小时的有界退避重试，成功后才恢复 7 天周期，不能因一次
  失败再静默等待完整周期。
- `SNAP-020C`：持有 `campus_connector:manage` 且完成近期 MFA step-up 的管理员可以手动触发完整同步。
  请求只能引用该学校已批准、健康且启用的 `roster_snapshot_upload` operation，不得携带 SQL、目标地址、
  路由、账号、口令或 secret reference。
- `SNAP-020D`：手动同步任务必须持久化并记录管理员、原因、学校、operation、状态、领取次数、稳定结果
  分类和时间；同校同 operation 同时最多一个进行中任务。连接器领取使用有限租约、有限重试和 24 小时
  总期限，应用或节点重启不得静默丢单，管理员原因不得下发校园节点。
- `SNAP-021`：依赖名册的实名信息校验、学号邮箱和学校手机号匹配在快照超过硬失效阈值后必须停止
  形成新的对应凭据。
- `SNAP-022`：界面应显示方法暂时不可用及其他选择，不向普通用户暴露 Oracle、表名或内部错误。
- `SNAP-023`：系统不得因为一次同步失败立即撤销全部已有凭据；撤销只基于成功激活的新事实或
  已定义的凭据到期规则。
- `SNAP-024`：每次成功激活后必须重新评估依赖该名册的活动凭据，学生已不符合准入条件时应撤销
  或进入复核状态。
- `SNAP-025`：名册依赖方法必须在**凭据形成或激活的最终事务**中重新检查当前 active snapshot、
  快照新鲜度和学籍准入，而不是只相信申请创建、OTP 发送或页面打开时的结果。
- `SNAP-026`：OTP 或其他挑战记录应保存发起时使用的 snapshot revision；最终 revision 变化时仍按
  当前快照重新评估，不得因为挑战已发出而绕过硬失效阈值。
- `SNAP-027`：快照在申请进行中超过硬失效阈值时，不形成凭据，返回稳定的可重试依赖错误并映射到
  “学校数据服务正在更新”的用户状态；用户可以选择不依赖名册的健康方法。
- `SNAP-028`：如学校需要短暂 grace period，必须显式配置期限和适用方法，并在凭据元数据与审计中
  记录；默认不存在隐式宽限。

推荐初始值为每 7 天同步、8 天告警、14 天停止新的名册依赖认证；同步失败应使用有界退避重试，且管理员可通过受审计的校园连接器命令手动触发完整同步。具体值需在上线前根据
源系统更新周期确认。

### 13.6 学籍准入规则

当前学生不能只由“学号存在”判断。学校准入配置和测试覆盖以下规则：

- `ENR-001`：哪些学籍状态允许认证。
- `ENR-002`：是否必须在校。
- `ENR-003`：是否必须完成当前学期注册。
- `ENR-004`：休学、保留学籍、交换、预科、留学生和已毕业状态如何处理。
- `ENR-005`：新生在正式入库前走哪一种临时流程。
- `ENR-006`：从多段符合准入的学籍中选择当前活动学籍时，依次使用明确当前标志、有效区间、
  规范化 `RXNJ`、培养层次和稳定记录 ID；任一层出现无法解释的冲突时进入人工处置。
- `ENR-007`：状态映射或当前学籍选择规则未完成时，名册依赖方法不得上线。

### 13.7 Oracle 权限与同步模式

- `SNAP-029`：Navicat、DBeaver 或其他 GUI 能建立会话，只能证明网络、认证和至少一个探测查询可用；
  不证明账号对目标 owner/view、全部必需列、Flashback、LogMiner、数据字典或增量游标拥有同步权限。
- `SNAP-030`：生产同步只能使用用户明确指定的既有账号。不得为 StuHelper 创建、更换或调整 Oracle
  账号与权限；若现有账号是对象 owner 或具有较宽权限，只记录风险并继续由客户端强制固定 `SELECT`，
  不得通过尝试 DML、DDL、PL/SQL、未批准对象读取或权限变更来验证边界。
- `SNAP-031`：上线前只读预检必须确认实际 session 用户、目标对象 owner、必需列、可读行、源时间
  字段、主键/唯一键、状态代码、获批传输模式和实际 grants；预检报告只保存聚合结果和授权边界，不导出
  学生明细或秘密。
- `SNAP-031A`：TCPS 是默认模式。学校现有路径只能通过固定 SSH 跳板时，允许校园节点运维层预建单一
  loopback local forward；必须钉住 SSH host key 和远端 Oracle 1521，禁止公网监听、动态转发、SOCKS、
  listener redirect 和任意目标，且不得把 SSH 隧道描述为 Oracle TCPS。
- `SNAP-032`：在没有可靠变更游标和删除事件契约时，默认采用周期性完整快照。完整快照必须使用单次
  一致性读取，或在多分片读取时固定同一受支持的 SCN，并按 `SNAP-010`—`SNAP-019` 原子激活。
- `SNAP-033`：只有数据 owner 明确提供单调、不可回退的更新时间/序列/SCN、稳定主键和删除或失效
  事件语义时，才允许增量同步；仅有 `updated_at` 而没有删除语义不构成完整增量方案。
- `SNAP-034`：不得把 `ORA_ROWSCN` 默认当作精确逐行更新时间。未启用 `ROWDEPENDENCIES` 时它可能是
  块级值，即使启用也不保证等于精确提交 SCN；采用前必须由 DBA 确认表属性并通过遗漏/重复测试。
- `SNAP-035`：Flashback Version Query、LogMiner、GoldenGate 或其他 CDC 需要额外对象权限、日志配置、
  保留窗口和运维责任，不能从普通 `SELECT` 或 GUI 登录权限推断。未获学校 DBA 明确授权时不得尝试
  启用 supplemental logging、读取 redo 或申请广泛数据字典权限。
- `SNAP-036`：即使启用增量，也必须定期生成完整快照做集合对账，验证新增、更新、删除、状态变化和
  总量；差异超过门禁时停止增量激活并保留上一成功版本。
- `SNAP-037`：增量批次必须记录闭合的 `(from_cursor, to_cursor]`、源截止时间、行数、删除数、校验和、
  schema 版本和重放状态；导入必须幂等，游标只有在目标事务成功提交后才能推进。
- `SNAP-038`：分块读取必须使用稳定 keyset 和同一源截止点，不能用无固定排序的 offset 分页；连接器
  中断后从最后成功批次恢复，并在完成后执行完整性门禁。
- `SNAP-039`：学校无法提供安全增量条件时，不以“性能更先进”为理由自行建设 LogMiner。学生名册
  规模允许时，完整快照通常比未经授权的 CDC 更简单、更可审计，也能正确处理从源集合消失的记录。
- `SNAP-040`：同步任务不得执行 DDL、DML、存储过程或会改变 Oracle session/数据库安全配置的操作；
  任何超出批准 `SELECT`/`READ` 边界的需求都必须由学校 DBA 另行评审和授权。

## 14. 凭据、学籍与学生资格

### 14.1 凭据状态

单个凭据的目标状态模型为：

```text
pending → active → expired
                 ↘ revoked
pending → rejected
active  → review_required → active / revoked
```

- `CRED-001`：凭据必须记录用户、学校、方法、受保护主体标识、通过时间、状态和有效期。
- `CRED-002`：自动方法的失败尝试不得被写成活动凭据。
- `CRED-003`：同一方法重试应保留审计历史，但不能产生多个相互竞争的活动身份。
- `CRED-004`：人工材料凭据、临时新生凭据和学校策略要求复核的凭据必须有 `expires_at`。
- `CRED-005`：撤销和过期必须立即从资格派生结果中移除，不等待登录 token 到期。
- `CRED-006`：同一学校学籍主体已经绑定其他活动用户时，必须产生稳定的内部冲突结果并进入账号
  找回或人工核查；不得直接把数据库唯一约束错误返回用户，也不得静默抢占原绑定。

### 14.2 聚合学生资格

用户在某学校具备学生资格，当且仅当：

1. `ELIG-001`：至少存在一个当前活动、未过期、满足学校策略的凭据；
2. `ELIG-002`：凭据按该方法的 `roster_dependency` 满足名册要求，或具有学校配置认可的独立证据；
3. `ELIG-003`：没有生效的主体冲突、撤销或风险冻结；
4. `ELIG-004`：消费方额外要求得到满足；
5. `ELIG-005`：资格由当前事实实时派生，并携带可失效缓存的单调 revision。

`ELIG-006`：资格响应只包含以下最小必要信息：

- 是否符合；
- 学校稳定代码；
- 资格类别，例如正式学生或临时新生；
- 使用的凭据种类；
- 有效期；
- 评估时间和可用于缓存失效的版本。

- `ELIG-007`：不得向普通消费方披露身份证件号、材料、完整邮箱、手机号、姓名或学校密码。

### 14.3 多学号和升学

- `ENR-010`：一个用户可以先后绑定本科、硕士、博士或跨校学号。
- `ENR-011`：每个学号对应独立学籍关系、来源证据、有效区间和状态。
- `ENR-012`：历史学号不得因新学号通过而被覆盖。
- `ENR-013`：证件号 HMAC 可以作为检测“可能是同一自然人”的高敏内部证据，但跨账号合并仍需
  受控确认。
- `ENR-014`：不得仅凭同名、同手机号或相似邮箱自动关联两段学籍。
- `ENR-015`：对外只暴露当前业务需要的学籍，不默认暴露完整教育历史。

## 15. 账号附加凭据与平台账号绑定

### 15.1 手机号绑定

现行《网络安全法》要求信息发布、即时通讯等服务在提供相关服务时取得真实身份信息；《互联网用户
账号信息管理规定》第九条列举的认证方式包括移动电话号码、身份证件号码或者统一社会信用代码等。
因此，StuHelper 选择“首次内容发布前必须绑定已验证手机号”属于明确的产品风控策略，不应对外表述
为法律只允许手机号这一种方式。法规依据见[现行《网络安全法》第二十六条](https://www.cac.gov.cn/2025-12/29/c_1768735112911946.htm)
和[《互联网用户账号信息管理规定》第九条](https://www.cac.gov.cn/2022-06/26/c_1657868775042841.htm)。

- `PHONE-001`：完整规范化手机号以 Casdoor 用户 `Phone` 为唯一可写权威源。StuHelper PostgreSQL 保存一份
  应用受权范围内可读的完整值投影、脱敏展示值和带密钥唯一性 HMAC，用于联系、发送、唯一性及本地业务判定；
  该完整值是可从 Casdoor 重建的只读投影，不是第二权威源。所谓“明文投影”是指受权业务可获得完整号码，
  不授权在日志、API 响应、报表或无保护的通用列中暴露裸值；静态存储、备份和副本仍必须受到加密和访问控制。
- `PHONE-002`：Casdoor `Phone` 字段非空不等于已完成任一具体验证方法。PostgreSQL 手机号验证凭据必须记录
  用户、号码 HMAC、来源方法、`verified_at`、`last_confirmed_at`、状态、有效期和单调 revision；业务门槛只读取
  该凭据，不从 OIDC claim 或 Casdoor 字段非空直接推断验证方法。
- `PHONE-003`：手机号绑定与学生认证是两个独立流程。学生认证页面不得把手机号作为完成步骤；用户
  可以先完成学生认证，在首次发帖或进入其他明确配置的账号级能力时再绑定手机号。
- `PHONE-004`：当前目标内容发布策略要求一个活动手机号验证凭据。该策略只限制发布类能力，不影响
  浏览公开内容、管理学生凭据或完成学生认证；具体受限能力必须由 capability/策略显式列举。
- `PHONE-005`：绑定流程要求用户主动输入中国大陆手机号；即使当前学生快照或 LDAP 已有手机号，
  也不得把完整学校号码自动填入页面、向用户展示或在没有当次用户提交时静默写入 Casdoor。LDAP 登录成功、
  LDAP `Mobile` 非空或学生认证成功都不能自动绑定手机号。
- `PHONE-006`：北航学校数据校验路径使用当前已绑定的有效学生主体中的规范学号和姓名；如当前账号没有
  可信主体，可要求用户同时输入学号和姓名并重新与快照匹配。手机号必须始终由用户当次手工输入。
- `PHONE-007`：北航当前产品策略将“规范学号 + 姓名 + 用户手工输入手机号”与当前学籍快照全部一致
  定义为 `school_roster_phone_match` 手机号验证方法，匹配成功时可以免短信，直接进入 Casdoor 绑定和投影激活流程。
  北航配置默认启用该方法。
- `PHONE-008`：学校号码为空、格式错误、快照陈旧，或学号、姓名、手机号任一项不匹配时，系统向用户输入的
  号码发送腾讯云短信 OTP；不得提示“与学校预留号码不一致”，避免泄露学校数据或阻止用户使用已
  更换的新号码。
- `PHONE-009`：`sms_possession` 凭据只有在验证码短期有效、一次性消费、尝试与发送限流通过后形成；
  短信发送成功本身不代表验证成功。Redis 或限流依赖不可用时 fail closed。
- `PHONE-010`：学校目录匹配证明的是受控数据源的一致性，短信 OTP 证明的是当次号码接收能力；两种
  方法的 `method` 和 `assurance` 不得合并成一个无来源的 `phone_verified=true`。
- `PHONE-011`：写入顺序采用可恢复操作：先保存不授予权限的 pending 操作和号码 HMAC 预占，完成所选验证方法后
  由后端更新 Casdoor，再从已成功的 Casdoor 值刷新本地完整值投影、HMAC 和手机号凭据。任一步失败都不得满足
  发布门槛，并由幂等重试或对账修复。不得假设 Casdoor 与 PostgreSQL 存在分布式事务。
- `PHONE-012`：对账以 Casdoor 当前值覆盖或清空 StuHelper 只读投影，并在受控内存重算 HMAC；outbox 和普通事件只保存
  用户内部 ID、操作 ID 和 revision，不保存完整手机号。Casdoor 已更新而本地投影暂未同步时，业务可显示“数据同步中”
  并 fail closed，但不得回写旧投影到 Casdoor。如 Casdoor 当前号码 HMAC 与活动手机号凭据不一致，必须撤销旧凭据，
  在新号码重新完成 `school_roster_phone_match` 或 `sms_possession` 前不得满足发布门槛。
- `PHONE-013`：首次绑定、换号、解绑和管理员纠错必须相互区分。换号和解绑要求 step-up MFA、重新
  验证、风险检查和审计；所有修改和解绑都由 StuHelper 个人中心后端调用 Casdoor 完成，不存在直接修改本地投影的用户
  或管理员接口。旧凭据必须撤销并增加 revision。
- `PHONE-014`：同一规范化手机号默认只能属于一个活动 StuHelper 账号；冲突使用不可枚举文案和统一
  账号找回入口，不显示另一账号、学校号码来源或数据库唯一约束。
- `PHONE-015`：手机号及其 HMAC、匹配结果、OTP 和 provider 响应不得进入日志、Trace、指标 label、
  前端埋点或会话回放；普通界面只显示脱敏号码和验证方法。
- `PHONE-016`：无论 `sms_possession` 还是 `school_roster_phone_match`，都不得创建学生凭据、合并两个
  StuHelper 账号、关联历史学号或替代学校 SSO、实名信息校验、邮箱和人工材料证明。

### 15.2 QQ 平台账号绑定

- `BIND-001`：QQ 绑定独立于学生认证；未绑定 QQ 的用户仍可完成学生认证。
- `BIND-002`：学生认证成功不会自动信任用户在网页手工填写的 QQ 号。
- `BIND-003`：QQ 号只能通过机器人私聊上下文、签名 admission token 或其他可验证平台事件绑定。
- `BIND-004`：一次性绑定码必须短期有效、服务端哈希保存、一次性消费并限制尝试次数。
- `BIND-005`：一个 QQ 号不得同时绑定多个活动 StuHelper 账号；冲突进入找回或人工处置。
- `BIND-006`：解绑、换绑和管理员纠错必须进行 step-up MFA、风险检查和审计。
- `BIND-007`：QQ 昵称和群名片只可作为临时展示信息，不写入学生认证主体。

## 16. 群聊入群准入服务

### 16.1 服务边界

- `ADM-001`：群聊准入是独立模块，可以选择“要求学生认证”或其他准入方式。
- `ADM-002`：群聊准入不得在自己的会话中复制一个长期 `student_verified` 布尔值作为真源。
- `ADM-003`：每次需要做出准入决定时，通过受控接口评估当前资格；短时缓存必须能被凭据事件失效。
- `ADM-004`：学生认证服务不得接收群号、禁言时间、踢出阈值等群策略字段。
- `ADM-005`：群会话可以等待一个用户完成独立学生认证，但不能改变认证方法的业务规则。
- `ADM-006`：同一 `platform + guild_id + platform_subject` 在全部进行中状态中，同一时刻至多存在
  一个 admission session。该不变量必须由数据库部分唯一约束或等价强约束保证，不得只依赖应用层
  “先查再写”。
- `ADM-007`：状态重命名或新增时必须同步更新活动会话唯一约束、状态 CHECK、pending action、提醒
  和超时扫描索引，并用迁移先收敛已有重复记录。

### 16.2 群策略

每个群可以配置：

- `POL-001`：是否要求学生认证。
- `POL-002`：允许哪些学校，或是否允许任意已认证学校。
- `POL-003`：是否允许临时新生身份。
- `POL-004`：最低凭据剩余有效期或最大认证年龄。
- `POL-005`：入群申请阶段审核还是入群后禁言验证。
- `POL-006`：登录/绑定等待时间、认证等待时间和人工审核等待时间。
- `POL-007`：提醒频率、超时动作和失败拉黑策略。
- `POL-008`：依赖不可用时的等待、提醒、重试、告警、保持禁言和取消会话策略。
- `POL-009`：是否在成员入群后持续检查资格，以及资格撤销后的提醒、禁言、移除或仅告警动作。
- `POL-010`：故障策略不得配置为“资格未知时自动通过”“使用无界陈旧缓存放行”或“审核制入群
  请求自动同意”；准入授权决定始终 fail closed。
- `POL-011`：默认学生认证策略只在准入时检查。未开启持续成员治理时，凭据后续撤销只影响新的
  准入决定，不得无条件踢出现有成员。

### 16.3 入群会话状态

目标状态表达 admission 自身进度，避免用 `verified` 混淆学生认证。状态转换以事件表为准，流程包含
分支和回退，不是所有会话都经过相同节点的线性链：

| 当前状态 | 事件 | 条件 | 目标状态 |
|----------|------|------|----------|
| `created` | 需要关联账号 | 尚无可信平台绑定 | `awaiting_account_link` |
| `created` / `awaiting_account_link` | 账号关联完成 | token、用户和平台主体一致 | `awaiting_requirements` |
| `awaiting_requirements` | 资格评估通过 | 当前 eligibility revision 有效 | `eligible` |
| `awaiting_requirements` | 人工申请已提交 | 申请与当前用户一致 | `pending_manual_review` |
| `pending_manual_review` | 凭据激活 | 当前群策略满足 | `eligible` |
| `pending_manual_review` | 审核驳回 | — | `rejected` 或返回 `awaiting_requirements` |
| `eligible` | 创建放行动作 | revision 未变化 | `action_pending` |
| `eligible` | 凭据撤销或策略变化 | 尚未创建有效动作 | `awaiting_requirements` |
| `action_pending` | eligibility revision 失效 | Koishi 尚未执行 | `awaiting_requirements` |
| `action_pending` | Koishi 执行成功 | 结果已回写 | `admitted` / `released` |
| `action_pending` | Koishi 执行失败 | 可重试 | 保持 `action_pending` |
| 任一进行中状态 | 用户取消、管理员取消或超时 | — | `cancelled` / `expired` |

- `STATE-001`：`eligible` 只表示本次群策略在某个 eligibility revision 上评估通过，学生凭据仍由
  学生认证服务持有。
- `STATE-002`：自动方法或既有凭据可以从 `awaiting_requirements` 直接进入 `eligible`，不得强制
  经过 `pending_manual_review`。
- `STATE-003`：`action_pending` 表示后端已决定放行但 Koishi 尚未成功执行；Koishi 回写实际结果后
  才能进入 `admitted` 或 `released`。
- `STATE-004`：放行动作必须携带 eligibility revision。凭据撤销、过期或策略变化使 revision 失效时，
  尚未执行的旧动作必须被 supersede 或取消，不得继续解禁。
- `STATE-005`：动作已经执行成功后的资格变化按 `POL-009` 持续治理策略处理，不把已完成会话倒退成
  等待态。
- `STATE-006`：状态转换、提醒、踢出、动作 supersession 和重试必须幂等并写审计。

### 16.4 QQ + Koishi 流程

```text
QQ 入群事件
    ↓
Koishi 获取群策略并创建/复用 admission 会话
    ↓
平台账号已绑定？── 否 → 签名链接关联当前 StuHelper 用户与 QQ
    │
    是
    ↓
准入服务查询学生资格
    ├── 已满足 → 产生幂等放行动作
    ├── 未满足 → 引导到独立学生认证入口
    └── 人工审核中 → admission 只等待结果
                         ↓
学生凭据激活事件 → admission 重新评估策略
                         ↓
Koishi 执行同意/解禁并回写结果
```

### 16.5 Koishi 约束

- `KOISHI-001`：Koishi 不保存权威学生身份、人工审核决定或群准入最终事实。
- `KOISHI-002`：Bot 内部接口只接受受限服务凭据，不接受用户 Cookie 或用户 JWT。
- `KOISHI-003`：每个执行动作必须有稳定幂等键；重复拉取不得重复解禁、踢出或发送高频提醒。
- `KOISHI-004`：执行成功和失败都必须回写，后端不得把“已决定”误报为“QQ 已执行”。
- `KOISHI-005`：后端暂时不可用时，审核制入群申请不得自动放行；已经入群并禁言的成员应保持
  安全状态并重试，不因瞬时故障直接踢出。
- `KOISHI-006`：管理群命令只能请求后端执行受权操作，Koishi 本地管理员身份不能直接授予学生凭据。
- `KOISHI-007`：后端 PostgreSQL durable outbox 是待执行 QQ 动作的唯一权威队列；SSE、长连接、
  `LISTEN/NOTIFY` 或其他实时通道只负责低延迟唤醒，不得成为唯一消息副本。
- `KOISHI-008`：Koishi 通过按 `platform + bot_self_id` 限定的 claim 接口取得动作。claim 必须使用
  数据库竞争锁或等价原子租约，支持多实例竞争但同一 dispatch attempt 至多有一个有效执行者。
- `KOISHI-009`：实时通道断开时必须保留有界周期扫描作为修复路径；扫描、连接重建和 Koishi 重启都
  从 durable outbox 恢复，不能依赖 Koishi 本地内存或本地数据库重建权威动作。
- `KOISHI-010`：动作结果回写必须携带稳定 action ID、session ID、动作类型和 dispatch attempt；后端
  对过期租约、旧 attempt、已 supersede 动作和重复 ACK 幂等拒绝或吸收，防止延迟回包覆盖新状态。
- `KOISHI-011`：每个活动 bot 实例最多维持一条受认证动作流，服务端发送心跳并关闭写超时；客户端
  采用带 jitter 的有界指数退避，稳定连接后再重置退避。连接故障不得触发无界并发重连。
- `KOISHI-012`：Koishi 与后端日志只记录状态转换和受控关联 ID。重复断线错误必须采样、限频或聚合，
  成功心跳、空扫描和每次普通重连不得持续写 info/warn；QQ 号、群号、bot 号和 message ID 使用批准
  的不可逆关联值或脱敏值，禁止记录请求/响应正文、token、学校密码和学生证明。
- `KOISHI-013`：运维主要依赖指标而非重复文本日志，至少包括流连接状态、重连次数、outbox 待处理数
  与最老年龄、claim/ACK 延迟、lease 失效、重试、dead letter、supersede 和按动作类型的成功率；
  label 遵守 `OBS-010` 的低基数限制。
- `KOISHI-014`：在当前单平台、少量 bot 规模下，SSE 唤醒 + PostgreSQL outbox + claim/lease/ACK +
  周期扫描是目标基线，不为“企业级”标签直接引入 Kafka、RabbitMQ 或 NATS。只有容量测试证明数据库
  唤醒或连接数越过获批阈值时，才可引入消息代理；迁移后 outbox、幂等键和结果栅栏仍须保留。

### 16.6 无 admission token 的场景

- `ADM-008`：用户可以随时在主站独立完成学生认证和 QQ 绑定。但没有有效 admission token 或可
  关联的待处理 QQ 会话时，页面不得声称“已经通过某个群”或“将自动解禁”。群聊准入服务在下一次
  事件或会话归并后重新判断。

## 17. 旧数据一次性清理与无兼容切换

产品 owner 已明确决定：旧学生认证事实不具备继续服务、迁移或备份价值。上线切换采用干净重置，
所有用户在新系统中重新取得凭据。此决策只扩大本节所列数据清理范围，不授权删除用户账号、QQ、
手机号、群策略或普通业务数据。

### 17.1 清理边界

- `MIG-001`：必须物理删除旧 `user_profiles` 学生认证行，不保留学校、学号、表单、认证状态、方法、
  审核原因、同意、通过时间、中性壳行或迁移标记。OpenFGA 旧投影通过清理前写入的负向 outbox
  任务撤销，任务执行时只读取新学生认证权威源，不依赖旧 profile 行。
- `MIG-002`：必须删除旧学生认证凭据、旧实名记录（含姓名、加密证件号和材料引用）、旧新生申请、
  旧人工材料元数据、旧/预发布学生认证申请、尝试、主体、冲突、资格 revision 和 outbox。
- `MIG-003`：必须清空旧 `academic.buaa_students` upsert 名册和任何预发布目标快照；上线后只有新一次
  完整同步通过质量门禁并原子激活，依赖名册的方法才可启用。
- `MIG-004`：不得删除 `users`、Casdoor 用户或手机号、`user_qq_bindings`、手机号投影和凭据、群策略、
  黑名单、课程、内容、授权账本及其他非学生认证业务事实。
- `MIG-005`：旧实名照片、新生材料和预发布人工审核材料必须从私有对象存储物理删除。数据库切换可
  先把对象键写入专用瞬时删除队列；成功删除对象后必须物理删除队列行，不得把该队列当作备份或
  长期审计档案。
- `MIG-006`：与旧认证直接对应的用户通知和含身份材料/结果的旧认证审计载荷必须一并删除；切换本身
  只记录不含用户明细和旧证据的聚合运维事件。

### 17.2 权威切换与进行中准入

- `MIG-010`：切换后学生资格只读取目标活动凭据；不得保留 profile fallback、双写、影子双读、宽限期、
  `legacy_migrated` 凭据或按用户分批选择旧真源。
- `MIG-011`：所有未执行的旧 `release` 动作必须标为 stale；处于 `eligible`、`action_pending` 或旧人工
  审核等待态的 admission 会话必须回到 `awaiting_requirements`，由用户在新系统重新认证。
- `MIG-012`：已经执行完成的 `admitted/released` 会话只作为 admission 历史保留，不得被解释为当前
  学生资格；后续重新入群或新策略判断必须实时读取目标凭据。
- `MIG-013`：切换 admission 状态名时，必须在同一受控发布中重建 `ADM-006` 的活动会话唯一约束、
  状态索引和 revision 栅栏，并先收敛重复进行中会话。
- `MIG-014`：旧学生认证、旧实名、旧 admission 内嵌 SSO/邮箱/新生材料写入口必须停止注册；OpenAPI、
  Web、Admin 和 Koishi 只能调用目标学生认证域，避免清理后旧数据再次产生。
- `MIG-015`：旧正向 profile/角色/outbox 投影必须取消或覆盖为否定投影；不得因为清除了数据库事实而
  在 Casdoor、OpenFGA、缓存或机器人本地状态中继续保留可授权的“已认证学生”结果。
  Casdoor 如存在历史 `verified_student` 业务角色成员关系，切换时必须通过 Casdoor
  管理接口删除该成员关系并验证为零，不得因此删除 Casdoor 用户、手机号或登录身份。
- `MIG-016`：单向清理必须先使用数据库排他锁收敛已在执行的旧写事务，并在删除后建立
  不可回退的数据库写入栅栏：旧 profile、identity、freshman 材料/申请和 upsert 名册不得
  重新写入，学生凭据新写入必须关联目标学生认证申请。不得只依赖“尽快替换旧容器”来
  防止清理窗口中的回写。

### 17.3 执行与回滚

- `MIG-020`：清理必须使用独立、可审查的单向 migration，明确列出删除和保留对象；migration 不创建
  备份表、不导出旧数据、不生成可恢复摘要，也不得把原始值写入日志。
- `MIG-021`：数据库清理与 active admission 动作失效必须在同一事务提交；对象存储删除通过可重放、
  有租约的瞬时队列最终完成，依赖暂时不可用时持续重试且不得丢失待删除对象键。
- `MIG-022`：数据清理不可回滚。应用只能回滚到兼容目标 schema、仍禁用全部旧写入口且只读取新凭据
  真源的版本；不得回滚到会重新注册旧 profile/identity/freshman API 或重新产生旧事实的版本。任何
  down migration 都必须明确拒绝伪造、恢复或重新授予旧学生资格。
- `MIG-023`：上线前必须在生产等价副本演练清理 SQL、外键顺序、对象删除、旧投影撤销和重新认证流程；
  上线后只验证剩余数量为零和新流程可用，不读取、导出或展示已删除的个人明细。
- `MIG-024`：删除操作完成后，数据库与对象存储的零剩余验证、旧写入口不存在验证以及非目标域未受
  影响验证必须作为上线门禁；任一失败均不得启用学校验证方法。
- `MIG-025`：包含旧认证事实的既有逻辑整库备份、物理基准备份、对象存储副本和可恢复到清理前状态
  的 WAL 必须在生产切换清单中逐类盘点。现有 `infra/ops/prod-deploy.sh` 会在 migration 前同时创建
  逻辑备份和物理基准备份，因此不得未经调整直接用于执行本次不可恢复清理。若要满足“任何备份均
  不保留旧认证事实”，必须先取得删除或不可恢复销毁受影响整份恢复介质的独立运维授权，并评估其
  对课程、内容、授权账本等非目标域恢复能力的影响；在该授权和替代的清理后恢复锚点方案完成前，
  生产切换必须阻断。不得以覆盖、修改或选择性重写既有备份文件来伪装合规处置。

## 18. 服务契约要求

具体路径和 schema 由实施阶段确定，本文只规定能力边界。

- `API-001`：新增或修改接口必须先更新 `server/api/openapi.yaml`，再生成 Go 和 TypeScript 类型，
  不得手改生成产物。
- `API-002`：用户接口、管理接口和内部消费方接口必须使用相互独立的认证与授权边界；内部服务凭据
  不得由浏览器获得，用户 Cookie 或用户 JWT 不得替代 Koishi 服务凭据。
- `API-003`：所有状态、失败原因和依赖错误必须使用稳定、可文档化的机器码；不得让客户端解析中文
  文案、数据库错误或 HTTP 响应时间推断业务状态。

### 18.1 用户侧能力

- `API-USER-001`：查询可认证学校和各学校当前可用方法。
- `API-USER-002`：创建或继续学生认证申请。
- `API-USER-003`：启动并完成一种验证方法。
- `API-USER-004`：查询申请、凭据和聚合资格状态。
- `API-USER-005`：创建受控拍摄交接、上传摄像头材料并提交人工审核。
- `API-USER-006`：取消未完成申请或切换方法。
- `API-USER-007`：查看隐私说明、有效期、账号找回和人工核查入口。
- `API-USER-008`：查询脱敏手机号状态、创建绑定操作、确定服务端允许的验证路径、发送/校验短信
  OTP，并在成功后查询手机号凭据；免短信与短信分支均由后端判定，成功后均必须先更新 Casdoor、再刷新
  StuHelper 只读投影，客户端不得直接提交“学校号码已匹配”或“免短信”结论。
- `API-USER-009`：换号和解绑使用独立 step-up 契约，不复用首次绑定接口，也不接受客户端提交旧凭据
  状态或 revision 作为授权依据；接口只调用 Casdoor 变更编排，不提供“仅修改 StuHelper 投影”的参数或路径。

### 18.2 管理侧能力

- `API-ADMIN-001`：学校、验证方法和名册依赖策略配置。
- `API-ADMIN-002`：适配器配置校验、健康查询与启停。
- `API-ADMIN-003`：学籍快照版本、质量门禁、激活和回滚。
- `API-ADMIN-004`：人工审核列表、详情、补充、批准和驳回。
- `API-ADMIN-005`：凭据撤销、复核、账号找回和主体冲突处置。
- `API-ADMIN-006`：群策略、会话、动作和黑名单管理。
- `API-ADMIN-007`：审计查询、材料访问申请和数据访问留痕。
- `API-ADMIN-008`：学校适配器版本、声明式学号策略、手机号匹配方法、字段映射和灰度启停；管理端不得接收
  任意脚本或显示学校服务账号秘密。
- `API-ADMIN-009`：校园连接器只读健康、节点版本、证书到期、允许操作和吊销状态；通用学校管理员
  不能修改三层路由、下载连接器私钥或读取内网凭据。

### 18.3 消费方能力

学生认证服务面向消费方提供：

- `API-CONSUMER-001`：按当前用户评估学生资格。
- `API-CONSUMER-002`：由可信内部服务按内部用户 ID 有界批量评估资格。
- `API-CONSUMER-003`：按学校、资格类型、有效期和凭据强度表达要求。
- `API-CONSUMER-004`：发布凭据激活、过期、撤销和复核状态变化事件。
- `API-CONSUMER-005`：返回可用于防陈旧缓存的单调版本或修订号。
- `API-CONSUMER-006`：批量查询必须有数量上限、超时、授权范围和审计，不能成为全库导出接口。
- `API-CONSUMER-007`：领域事件必须可幂等消费，并通过 outbox 或等价机制避免数据库提交成功但事件
  永久丢失。
- `API-CONSUMER-008`：消费方不得获得证件号、材料 URL、完整邮箱、手机号、姓名或其他验证证据。

### 18.4 账号级手机号门槛能力

- `API-PHONE-001`：内容发布等业务通过独立内部契约判断当前用户是否具有满足策略的活动手机号凭据；
  不得跨模块读取 Casdoor 表、`users.phone_*` 或学生快照手机号字段。
- `API-PHONE-002`：响应只包含是否满足、允许的保证等级、凭据 revision、评估时间和通用不满足原因；
  不返回完整号码、学校匹配结果、provider 响应或 OTP 状态。
- `API-PHONE-003`：手机号绑定、换号、解绑或撤销后必须增加 revision，并通过 outbox 或等价机制失效
  消费方缓存；Casdoor 字段变化但本地凭据尚未确认时默认不满足门槛。
- `API-PHONE-004`：学生资格查询不得隐式附带手机号门槛。消费方同时需要学生资格和手机号时，必须
  分别声明两个要求并得到可审计的组合结果。
- `API-PHONE-005`：浏览器无法获得 Koishi、校园连接器或内部消费方服务凭据；连接器也不能调用用户
  发布、群动作或管理员业务接口。

## 19. 用户界面与交互要求

### 19.1 设计方向

`UX-FLOW-001`：认证界面采用可信、克制、移动优先的单列布局，使用现有品牌和语义色 token。
不得为了“现代化”采用夸张大标题、娱乐化插画、彩虹渐变、玻璃拟态堆叠或与安全场景不符的
游戏化效果。

视觉和交互原则：

- `UX-FLOW-002`：每一屏只有一个明确主操作；危险或取消操作不得与主操作同等强调。
- `UX-FLOW-003`：用步骤指示器展示当前位置、已完成步骤和剩余步骤，读屏器可获得同等信息。
- `UX-FLOW-004`：用方法卡片解释“需要什么、预计耗时、会提交什么信息、是否依赖学校服务”。
- `UX-FLOW-005`：逐步披露字段，不展示与当前方法无关的表单，也不提前申请摄像头等权限。
- `UX-FLOW-006`：加载、成功、失败、等待人工审核和依赖不可用必须有稳定、可恢复的页面状态。
- `UX-FLOW-007`：用户失败后可以重试、切换健康方法或进入统一人工核查，不必重新填写无关信息。
- `UX-FLOW-008`：不使用 emoji 充当功能图标；图标使用项目现有 SVG 图标库并提供可访问名称。
- `UX-FLOW-009`：动效只用于状态连续性，时长宜为 150–300 ms，并尊重
  `prefers-reduced-motion`；关闭动效不影响状态理解和操作完成。

### 19.2 学生认证页面

目标步骤如下：

1. `UX-FLOW-010`：**选择学校**：搜索、最近学校和学校认证状态；目录中未启用认证的学校不得
   显示为可直接申请。
2. `UX-FLOW-011`：**选择验证方式**：展示服务端能力驱动的方法卡片和当前可用性。
3. `UX-FLOW-012`：**完成验证**：只展示当前方法需要的字段、隐私说明和恢复帮助。
4. `UX-FLOW-013`：**查看结果**：展示学校、资格类型、方法、通过时间、有效期和下一步。

- `UX-FLOW-014`：页面必须支持独立进入。由群聊准入打开时，可以在顶部显示中性的来源提示：

> 完成学生认证后，发起方将重新检查您是否满足要求。

- `UX-FLOW-015`：不得显示未经后端 admission 重新评估的“已解禁”“已同意入群”等结论。
- `UX-FLOW-016`：“实名信息校验”方法卡片必须说明预计耗时、需要学号、姓名和身份证件号、StuHelper
  对本次原文的保存边界和可替代方法；卡片标题、步骤名和普通错误不出现“学籍”“Oracle”或内部比对字段，
  并按 `DOC-011` 显示真实、最小披露的服务端一致性校验说明。

### 19.3 表单与反馈

- `UX-001`：所有输入都有持久可见的 label，不以 placeholder 代替字段名。
- `UX-002`：格式错误在字段附近显示，并通过 `aria-describedby` 关联。
- `UX-003`：异步错误通过 `aria-live` 或 `role=alert` 宣告，不能只显示红色边框。
- `UX-004`：提交时按钮显示进度并防止重复提交；长操作提供可理解的等待状态。
- `UX-005`：触控目标至少 44×44 px，键盘可操作，焦点样式清晰可见。
- `UX-006`：正文与背景对比度至少 4.5:1，不仅依赖颜色表达状态。
- `UX-007`：支持 375、768、1024 和 1440 px 关键宽度，不出现横向滚动。
- `UX-008`：不禁止浏览器缩放；适当使用 `autocomplete`、`inputmode` 和语义化输入类型。
- `UX-009`：证件号字段默认遮蔽显示，并允许用户主动短暂查看；不得放入 URL 或页面分析事件。
- `UX-010`：SSO 跳转前说明将前往哪个学校；回跳后明确成功、取消或服务不可用。
- `UX-011`：认证 Web、移动 Web 和管理端必须复用经过验收的 Button、Input、Select、Textarea、
  FormField、Alert 和步骤组件，统一尺寸、边框、禁用态、加载态、错误态、焦点态和设计 token；不得
  复制当前页面中不可见边框、无样式 CTA 或仅靠父组件 scoped CSS 生效的实现。
- `UX-012`：刷新或跨设备交接后，应从服务端恢复非秘密的申请步骤和状态；密码、OTP、完整证件号和
  未提交拍摄帧不得进入 `localStorage`、URL 或可同步浏览器存储。
- `UX-013`：用户可见文案、错误、日期、倒计时和无障碍名称必须进入项目 i18n 与统一格式化链路，
  不得在同一流程散落互相矛盾的硬编码文案。

### 19.4 错误文案

- `UX-ERR-001`：普通用户不得看到数据库错误、唯一约束、名册枚举细节或内部主体标识。错误响应
  必须同时提供稳定机器码、通用用户文案和至少一个安全的可执行操作。

推荐分类：

| 场景 | 用户文案方向 | 可执行操作 |
|------|--------------|------------|
| 输入格式错误 | 指出本地格式问题 | 修改字段 |
| 信息无法匹配或主体冲突 | 无法使用本方式完成核验 | 重试、换方法、统一人工核查入口 |
| 方法暂不可用 | 当前方式暂时不可用 | 换方法、稍后重试 |
| 快照过期 | 学校数据服务正在更新 | 换用独立方法或稍后重试 |
| OTP 未到达 | 可能存在投递延迟 | 查看地址、等待、重发、改用发送邮件 |
| 人工审核中 | 已提交，预计由审核方处理 | 查看状态、补充材料 |
| 凭据已过期 | 学生身份需要重新确认 | 重新验证 |

- `UX-ERR-002`：不得明确返回“该学号存在但姓名错误”“身份证后四位不符”或“此邮箱已绑定另一个
  用户”等可枚举信息。
- `UX-ERR-003`：账号找回或人工核查入口必须对所有“信息无法匹配或无法完成本方式”的用户一致展示，
  不能只在服务端确认发生绑定冲突时显示；入口文案不得暗示另一账号或具体字段存在。
- `UX-ERR-004`：人工核查申请可以携带服务端生成的不可枚举原因类别和申请 ID，但不得让浏览器上传
  或展示“已绑定用户 ID”“已存在邮箱”等内部冲突证据。

### 19.5 人工审核拍摄体验

- `PHOTO-UX-001`：具备本机拍摄能力的浏览器首先显示权限用途，再由用户操作请求摄像头；不得在页面
  加载时弹权限框。
- `PHOTO-UX-002`：取景界面显示材料边界、清晰度提示、重拍和确认按钮，并在摄像头不可用、无后置
  摄像头或权限拒绝时立即提供二维码交接。
- `PHOTO-UX-003`：二维码旁必须说明有效期、目标申请和手机无需重新选择材料类型；二维码不得包含
  长期用户凭据或原始个人信息。
- `PHOTO-UX-004`：交接两端都显示同一申请的最小安全摘要，不展示完整证件号；任一端完成后另一端
  立即进入只读结果状态，不能重复提交。
- `PHOTO-UX-005`：上传显示真实进度和可重试失败；断网后允许在会话有效期内重试，不得静默丢失或
  把未完成上传显示为提交成功。
- `PHOTO-UX-006`：材料提交前必须显示用途、可见人员和保留期限，并记录用户确认的隐私说明版本。

### 19.6 管理后台体验

- `ADMIN-UX-001`：列表默认只显示脱敏字段，不加载材料。
- `ADMIN-UX-002`：详情按需申请短时材料访问权限，访问到期后必须重新授权。
- `ADMIN-UX-003`：审核决定、用户可见说明与内部风险备注必须分开。
- `ADMIN-UX-004`：高风险操作要求 step-up MFA，并在确认页展示目标学校、受保护用户摘要、原因和
  凭据影响。
- `ADMIN-UX-005`：筛选、分页和排序必须稳定；翻页或返回详情不能导致未提示的审核对象变化。
- `ADMIN-UX-006`：依赖健康、快照陈旧度和待审积压使用文本加语义状态，不只依赖颜色。
- `ADMIN-UX-007`：不得提供无审计的批量批准；确需批量操作时必须逐项校验授权、给出影响预览并
  为每一对象记录独立结果。

### 19.7 手机号绑定体验

- `PHONE-UX-001`：学生认证成功页不插入手机号必填步骤；只有用户进入首次内容发布或主动打开账号
  安全中心时，才以独立页面说明“用于内容发布账号核验和安全联系”，不能暗示手机号证明学生身份。
- `PHONE-UX-002`：页面只要求用户手动输入手机号，使用持久 label、`autocomplete="tel"`、
  `inputmode="numeric"` 和中国大陆区号说明；不得展示学校源号码、匹配状态或“学校预留号码”提示。
- `PHONE-UX-003`：服务端允许免短信时，页面直接显示“手机号已验证”及验证时间；不得显示“与教务
  库一致”。需要短信时在同一页面逐步展开验证码字段、倒计时、重发和改号入口，避免先展示无关字段。
- `PHONE-UX-004`：免短信与短信路径的最终成功页保持相同主结论，只可在账号安全详情中以用户可懂
  的方式显示“学校账号信息确认”或“短信验证码确认”；保证等级和内部 source code 不直接暴露。
- `PHONE-UX-005`：手机号不匹配、学校数据缺失和来源保证不足都不得显示错误；它们只意味着自动切换
  到短信路径。短信服务不可用时说明可稍后重试，不能让用户返回重做学生认证。
- `PHONE-UX-006`：绑定成功后原页面恢复用户发帖草稿和意图；刷新、后退、短信超时或跨标签页不得
  丢失非敏感草稿，但手机号、OTP 和 pending 操作秘密不得进入 URL、`localStorage` 或分析事件。
- `PHONE-UX-007`：换号和解绑页面必须显示对内容发布、账号找回和已有会话的影响，要求 step-up MFA
  并二次确认；不得把高风险操作与普通编辑资料混成一个保存按钮。

## 20. 隐私与安全

### 20.1 数据最小化

- `SEC-001`：只收集当前方法和当前审核所需信息。
- `SEC-002`：学生认证凭据保存受保护主体标识，不默认保存证明原文。
- `SEC-003`：证件号、邮箱、手机号、QQ 号和材料在日志中必须脱敏或使用不可逆关联标识。
- `SEC-004`：身份材料、证件号密文和学校密码不得进入通用分析、会话回放或前端错误采集。
- `SEC-005`：数据保留期限必须按数据类别配置；过期材料和旧快照以有界批次清理并保留审计结果。
- `SEC-006`：北航实名信息校验属于本地敏感个人信息处理路径；生产启用前必须完成合法性基础、显著告知、
  所需同意、个人信息保护影响评估、请求原文零持久化、访问最小化和保留期限核验。内部审计、凭据元数据
  和指标必须记录真实处理路径，不得伪造第三方 provider 的请求 ID、响应体或调用日志；用户可见文案按
  `DEC-010` 与 `DOC-011` 统一表述，两层不得互相污染。
- `SEC-007`：实名信息校验的请求/响应结构必须使用字段 allowlist 和日志 denylist；代理、WAF、APM、
  OpenTelemetry、错误追踪和会话回放都必须验证不会采集姓名、身份证件号或请求正文。
- `SEC-008`：学校服务账号秘密、校园连接器私钥和 Oracle/LDAP 凭据只允许通过 secret reference 注入；
  普通配置保存秘密引用和版本，不保存秘密值。秘密轮换不得要求修改学生认证业务数据。

### 20.2 访问控制

- `AUTHZ-001`：查看材料、审核、撤销凭据、修改学校配置、激活/回滚快照和修改群策略必须分别使用
  最小 capability，不得以一个泛化“管理员”权限覆盖全部操作。
- `AUTHZ-002`：学校管理员只能访问授权学校；群管理员不能查看学生证明材料，Koishi 管理员身份不
  自动获得任何学生认证管理能力。
- `AUTHZ-003`：材料详情要求有效的 step-up MFA，成功、拒绝和失败的访问都必须写安全审计。
- `AUTHZ-004`：后台列表不得返回可直接访问材料的对象 key、公开 URL 或可复用签名参数。
- `AUTHZ-005`：材料签名 URL 必须短期有效、限定对象和操作，并且只在当前授权请求成功后生成。
- `AUTHZ-006`：校园连接器节点注册、吊销、目标 allowlist 和证书轮换使用独立基础设施 capability；
  学校认证管理员只能选择已经批准的连接器能力，不能获得网络或 secret 管理权限。
- `AUTHZ-007`：快照可逆密文的解密能力必须绑定独立、可枚举的最小 capability，按学校和字段授予；
  每次解密写安全审计并记录用途、目标记录数和调用方。批量解密必须单独审批、限定数量并留档。普通
  业务读路径只使用 HMAC 比较和不可逆投影，不得申请解密能力；`ELIG-007`、`API-CONSUMER-008` 和
  `API-PHONE-002` 的消费方边界不因存在可逆密文而放宽。

### 20.3 防滥用

- `ABUSE-001`：自动方法按用户、学号哈希、学校、IP、设备风险和目标哈希设置组合限流。
- `ABUSE-002`：OTP、证件号和 SSO 失败尝试必须使用递增退避、尝试上限和临时锁定；成功后也不得
  立即清除用于发现分布式攻击的安全计数。
- `ABUSE-003`：限流依赖不可用时必须 fail closed，不继续冲击 Oracle、SSO、邮件或短信服务。
- `ABUSE-004`：不得用不同 HTTP 状态码、响应正文长度或显著响应时间差暴露学号、邮箱、证件号或
  主体绑定是否存在；本地格式错误不受此限制。
- `ABUSE-005`：人工审核提交必须限制频率、同时进行申请数、材料数量、单个大小和总大小。
- `ABUSE-006`：风险检测只能拒绝、延迟、要求额外证明或转人工，不得在没有学生证据的情况下自动
  授予学生身份。
- `ABUSE-007`：手机号短信按用户、号码 HMAC、IP、设备风险和失败次数组合限流；学校号码匹配路径
  也必须限流并使用等价错误时序，不能被用作查询学校是否保存某个手机号的 oracle。

### 20.4 审计

审计事件类别包括：

- `AUD-001`：申请创建、取消、方法切换和最终状态。
- `AUD-002`：自动验证方法、稳定结果分类和尝试序号，但不记录提交值。
- `AUD-003`：学籍快照同步、质量校验、激活、回滚和失败。
- `AUD-004`：人工材料访问、补充、批准、驳回和撤销。
- `AUD-005`：凭据创建、到期、复核、迁移和撤销。
- `AUD-006`：群资格评估、使用的 revision、决定、Koishi 动作和执行结果。
- `AUD-007`：管理配置变更前后差异的安全摘要、操作者、授权依据和关联工单或原因。
- `AUD-008`：审计中不得保存 OTP、学校密码、身份证件号原文、材料签名 URL、完整邮件正文或可用于
  重新执行敏感操作的凭据。带密钥版本的证件号 HMAC 可以在受控审计中保存，用于 `ENR-013` 的同一
  自然人识别和主体冲突排查；对该字段的读取本身必须计入访问审计。
- `AUD-009`：手机号 pending 操作、验证方法、保证等级、Casdoor 同步结果、激活、换号、撤销和对账；
  只记录用户内部 ID、受控关联 ID 和号码不可逆关联值，不记录完整号码或 OTP。
- `AUD-010`：学校适配器版本、连接器节点身份、调用操作、结果类别、延迟、熔断、证书轮换和吊销；
  不记录学校密码、服务账号、DN 中的用户学号、LDAP filter 实值、Oracle 行或内网响应正文。

## 21. 可用性、故障和观测

### 21.1 故障语义

- `FAIL-001`：Oracle 或快照同步失败属于数据依赖故障，不等于学生信息不匹配。
- `FAIL-002`：Redis、邮件、学校 SSO、短信或对象存储失败属于对应依赖故障，不等于用户认证失败。
- `FAIL-003`：未知依赖错误必须映射为稳定、可重试的服务不可用，不得伪装成业务拒绝。
- `FAIL-004`：自动认证无法完成时可以引导用户选择人工审核，但不得自动创建空材料申请或把失败
  尝试写成待审证据。
- `FAIL-005`：admission 无法读取当前资格时不得自动放行，也不得使用超过策略上限的陈旧缓存。
- `FAIL-006`：Koishi 执行失败必须保留待执行动作并按幂等策略重试，不能把后端决定改写为平台成功。
- `FAIL-007`：校园连接器离线、证书失效、版本不兼容或 allowlist 拒绝属于明确的内网依赖故障，只
  降级使用该连接器的学校方法；不得回退到生产直连内网、开发机代理，或回退到未显式登记的明文 LDAP
  路径。已批准的北航 RFC1918 IPv4:389 单 operation 例外不构成故障降级。
- `FAIL-008`：Casdoor 手机号更新成功但本地凭据未激活时，发布门槛保持不满足并进入受控对账；本地
  pending 成功但 Casdoor 更新失败时同样不激活，不能用“最终会一致”临时放行。

### 21.2 指标和告警

指标和告警覆盖：

- `OBS-001`：各学校、各方法的开始、成功、失败、取消和耗时。
- `OBS-002`：不含原始身份标识的限流、退避和锁定次数。
- `OBS-003`：OTP 投递接受率、验证率和延迟。
- `OBS-004`：SSO 适配器健康、错误分类、页面漂移和熔断状态。
- `OBS-005`：学籍快照最后成功时间、版本、行数变化、陈旧度、质量门禁和激活失败。
- `OBS-006`：人工审核队列长度、等待时间、补充率和材料访问拒绝。
- `OBS-007`：凭据过期、撤销、迁移差异和资格重算延迟。
- `OBS-008`：admission 等待人数、并行会话冲突、超时、资格决策和 Koishi 动作失败。
- `OBS-009`：入站邮件挑战处理延迟、邮件认证失败和重放拒绝。
- `OBS-010`：指标 label 不得使用学号、QQ、邮箱、手机号、姓名、证件号、材料 key 或群名等高基数
  敏感值；学校和群只使用批准的低基数稳定代码。
- `OBS-011`：Koishi 动作流连接状态、聚合重连次数、outbox 深度与最老年龄、claim/ACK 延迟、lease
  失效、重试、dead letter 和 supersede 数量；重复连接错误用指标和状态告警代替逐次 warn 日志。
- `OBS-012`：校园连接器在线状态、版本、证书剩余时间、学校/操作级成功率、并发、队列深度、超时、
  熔断和快照传输校验失败；不得把内网地址和节点秘密作为 label。
- `OBS-013`：本地实名信息校验成功率、稳定错误分类、延迟和限流，以及手机号学校匹配路径、短信路径、
  Casdoor 同步、完整值投影刷新、凭据激活和对账差异；不得记录或标记姓名、证件号、手机号或上游原始响应。

### 21.3 性能目标

上线前通过容量测试确定最终 SLO，目标行为如下：

- `PERF-001`：学校和方法查询不依赖实时 Oracle，并在适配器健康检查超时时返回已有可用能力和明确
  降级状态。
- `PERF-002`：本地名册单条匹配必须使用受支持索引；最终延迟 SLO 由脱敏生产规模容量测试确定。
- `PERF-003`：学籍快照暂存写入不得阻塞当前 active version 的读取，激活事务必须保持短小。
- `PERF-004`：admission 资格批量检查必须支持 Koishi 重启后的有界追赶，并对批量大小和并发设限。
- `PERF-005`：人工材料列表不得加载原图，不因对象存储延迟拖慢普通列表。
- `PERF-006`：所有后台任务必须遵守统一生命周期、取消、超时、幂等重试、死信和告警规则。
- `PERF-007`：容量测试必须覆盖正常峰值、依赖变慢、批量快照激活、凭据集中到期和 Koishi 重连，
  在 SLO、资源上限和失败策略获批前不得宣称生产容量达标。
- `PERF-008`：Koishi 容量测试必须测量每 bot 长连接数、空闲时数据库查询率、断线风暴、outbox 追赶
  时间和 ACK 吞吐。可以使用 PostgreSQL `LISTEN/NOTIFY` 或集中唤醒器降低空轮询，但必须保留周期
  扫描；引入外部 broker 的阈值必须由数据而不是架构偏好决定。
- `PERF-009`：校园连接器容量测试覆盖并发 LDAP user bind、用户取消、上游变慢、快照全量传输、增量
  追赶、断点恢复和证书轮换；任何队列都不得持久化用户学校密码。
- `PERF-010`：完整 Oracle 快照的时间和资源预算必须先以真实脱敏规模测量；只有完整快照无法满足获批
  新鲜度 SLO 且 `SNAP-033` 条件全部成立时，才以增量作为性能优化上线。

## 22. 验收场景

### 22.1 领域解耦

- `AC-DOM-001`：没有 QQ 绑定、没有入群会话的已登录用户可以独立完成学生认证。
- `AC-DOM-002`：学生认证记录中不存在 QQ 群号或 admission session 依赖。
- `AC-DOM-003`：一个已认证用户可以被课程和群聊两个消费方读取，而不重复认证。
- `AC-DOM-004`：群聊服务只能通过资格契约得到结果，不能直接修改学生凭据。
- `AC-DOM-005`：QQ 已绑定但学生未认证时，不会被误判为学生。
- `AC-DOM-006`：同一用户新增硕士或博士学号时形成新学籍关系，历史学号、证据和有效区间仍可审计。

### 22.2 学校配置与北航自动认证

- `AC-SCH-001`：新增测试学校只通过后端配置即可启用独立方法、名册依赖方法和条件方法，通用前端
  无需增加学校名称条件分支。
- `AC-SCH-002`：`schools` 目录中存在但未启用认证配置的学校不能创建认证申请；新增学校建议也不会
  自动进入认证白名单。
- `AC-SCH-003`：关闭一个异常适配器只让对应方法不可选，不影响同校其他健康方法。
- `AC-SCH-004`：条件依赖的学校 SSO 分别在“上游可靠证明学生”和“必须匹配活动名册”两个契约样例
  下得出正确结果，未知上游属性不会默认当作学生。
- `AC-SCH-005`：两个测试学校使用不同学号规则、邮箱派生和 SSO 适配器时，共享前端和人工审核表单
  不增加学校名称分支；非法正则、任意脚本和另校适配器配置被拒绝。
- `AC-SCH-006`：北航学号只有在适配器完成“学号 + 姓名”当前快照匹配后才能派生学号邮箱；客户端
  修改邮箱本地部分、大小写或别名不能绕过。
- `AC-SCH-007`：北航 LDAP user bind 与系统查询使用不同身份；完整 DN、filter、内网地址和服务口令
  不由浏览器提交，服务账号不能替代 user bind 验证用户密码。
- `AC-SCH-008`：LDAP 只支持明文连接但 operation 未显式启用固定 RFC1918 IPv4:389 风险例外、连接器
  版本不兼容或 secret reference 缺失时，北航 SSO 方法 fail closed，其他健康方法仍可使用。
- `AC-SCH-009`：任一需要 StuHelper 提交用户学校凭据的表单式或模拟登录适配器，在缺少
  系统 owner 授权、安全/合规评审，或遇到未知页面、验证码、MFA 与响应结构时不能生产启用或
  猜测成功；这一验收不将北航 LDAP 错误地实现为网页抓取。

- `AC-NET-001`：生产环境没有校园网通用路由，仍能通过已登记连接器完成一次受控 LDAP 验证和一个
  签名快照传输；尝试任意主机、端口、SQL、代理或 Shell 操作被连接器拒绝并审计。
- `AC-NET-002`：连接器证书吊销、节点身份伪造、签名错误、离线和版本不兼容分别触发稳定错误；不会
  自动回退到开发机、生产直连或未登记的明文 LDAP 路径，且只影响绑定到该连接器的学校方法。
- `AC-NET-003`：用户在 LDAP 请求期间取消、超时或使连接器断线后，学校密码不会出现在磁盘、Redis、
  持久消息、重试队列、日志、Trace 或崩溃转储中，恢复后必须重新输入。
- `AC-NET-004`：学校管理员可以查看连接器健康和适配器版本，但不能读取服务账号秘密、下载节点
  私钥、修改网络路由或获得其他学校操作权限。

- `AC-BUAA-001`：学号、姓名、当前学生状态和证件安全投影全部一致，且最终 snapshot revision 复查通过时，
  形成 `real_name_identity_check` 凭据；任一字段单独匹配都不能通过，全流程不调用外部实名 provider。
- `AC-BUAA-002`：源证件号为空或格式无效时，“实名信息校验”不可用，SSO 和邮箱方法仍可使用。
- `AC-BUAA-003`：证件号、姓名、学号或主体不匹配时不泄露具体错误字段；快照过期、密钥不可用或本地依赖故障
  不会被描述为用户信息不匹配。
- `AC-BUAA-004`：通过受信北航统一身份认证且主体规则满足时，形成 SSO 凭据。
- `AC-BUAA-005`：学校密码不会出现在数据库、Redis、日志、Trace 或前端采集数据中。
- `AC-BUAA-006`：邮箱由后端固定派生为精确学号邮箱，客户端替换邮箱被拒绝。
- `AC-BUAA-007`：同域别名、非学号前缀或快照中不存在的学号邮箱不能通过。
- `AC-BUAA-008`：接收验证码和发送验证邮件可以分别启停，并分别形成可审计凭据。
- `AC-BUAA-009`：入站挑战重复、过期、转发或发件人不可信时不会通过。
- `AC-BUAA-010`：北航 LDAP 遇到无效 TLS 证书、未知 schema/账号状态、未知认证控制或需要额外
  验证时停止方法并告警，不会猜测登录成功，也不会关闭证书校验。
- `AC-BUAA-011`：SSO 超时、熔断、并发限制和失败退避在沙箱故障注入中生效，学校密码不进入持久层、
  日志、Trace、Session、队列或客服数据。
- `AC-BUAA-012`：OTP 已发送后快照跨过硬失效阈值，正确回填验证码仍不会形成名册依赖凭据，并提供
  不依赖名册的健康替代方法。
- `AC-BUAA-013`：学号、姓名、身份证件号和手机号在快照中成对写入可逆密文与 HMAC，由同一源值原子
  生成并带密钥版本；缺少任一侧、密文无法解密、HMAC 不可复算或密钥版本缺失时，导入被质量门禁拒绝
  且不激活。受权路径可以解密单条记录并留下访问审计，未持有解密 capability 的模块无法取得明文。
- `AC-BUAA-014`：“实名信息校验”方法卡片、表单和普通错误只显示经批准文案，不出现“学籍核验”、Oracle、
  源表、内部字段或逐字段匹配结果；按 `DOC-011` 准确说明由 StuHelper 服务端执行一致性校验和请求原文
  保存边界，不出现腾讯云人脸核身、公安、政务或其他未实际调用的第三方背书。内部审计和凭据元数据经
  抽查确认使用真实方法值，未伪造 provider 请求 ID 或响应体。
- `AC-BUAA-015`：成功、失败、超时和重试后，用户本次提交的姓名、身份证件号及其请求正文都不会
  出现在 PostgreSQL、Redis、Casdoor、对象存储、队列、日志、Trace、APM、埋点或会话回放中。
- `AC-BUAA-016`：初次本地匹配成功但最终快照 revision 已变化、快照过期或学生主体不再匹配时不形成凭据；
  审计只保存结果类别、快照/密钥/适配器版本和时间，不伪造 provider 请求记录。

### 22.3 学籍快照

- `AC-SNAP-001`：Web API 没有 Oracle 凭据，Oracle 停机时仍可读取最后一份有效本地快照。
- `AC-SNAP-002`：新快照导入一半失败时，在线读取仍使用旧版本。
- `AC-SNAP-003`：上一版本存在、本次完整快照缺失的学生不会继续出现在当前名册。
- `AC-SNAP-004`：重复学号、未知状态或异常人数变化阻止自动激活并触发告警。
- `AC-SNAP-005`：快照超过硬失效阈值后，名册依赖方法停止新认证。
- `AC-SNAP-006`：成功新快照将学生标记为不符合准入后，相关资格在规定时间内撤销或进入复核。
- `AC-SNAP-007`：本科和研究生两段活动记录按学校批准的当前学籍规则稳定选择；`RXNJ` 相同或状态
  冲突时进入人工处置，不依赖数据库返回顺序。
- `AC-SNAP-008`：现有 upsert-only 导入器未经版本化和完整集合语义改造时，自动化检查阻止其作为
  active snapshot 的周期激活路径。
- `AC-SNAP-009`：快照激活与回滚都通过单一 active pointer 或等价事务完成，在线请求不会同时看到
  两个名册真源。
- `AC-SNAP-010`：质量门禁和新鲜度指标不包含学生明细，源时间倒退只有经过授权和审计才能激活。
- `AC-SNAP-011`：同一 GUI 账号可以普通查询但缺少目标列、Flashback 或 LogMiner 权限时，权限预检
  准确显示“仅可全量/权限不足”，不会因为连接成功就启动增量。
- `AC-SNAP-012`：没有可靠更新时间或删除事件的源只运行完整快照；从源集合删除的记录在下一完整
  快照激活后消失，不被 upsert 历史保留。
- `AC-SNAP-013`：启用增量的测试源使用闭合游标和删除事件，导入中断可幂等续跑，游标不会早于目标
  事务推进；周期完整对账能发现故意制造的漏变更。
- `AC-SNAP-014`：未启用 `ROWDEPENDENCIES` 的 `ORA_ROWSCN` 测试源不能被自动批准为精确逐行游标；
  未获额外授权时不会尝试 Flashback、LogMiner、supplemental logging 或广泛数据字典读取。
- `AC-SNAP-015`：多分片完整读取固定同一 SCN 或等价一致性截止点，源数据在读取期间变化不会产生
  混合时点快照；无法取得一致性语义时激活被阻止。
- `AC-SNAP-016`：生产同步配置只引用用户明确指定的既有账号 secret；门禁拒绝内置管理身份和任何
  非固定 SQL 接口，但不会因既有账号权限较宽而尝试整改 Oracle。验收只允许登录、只读数据字典和代码
  中固定的 `SELECT`，报告不得包含账号秘密或学生明细。
- `AC-SNAP-017`：默认配置显示 7 天同步、8 天告警、14 天硬失效；模拟一次周期失败后连接器按有界
  退避重试，成功后恢复 7 天周期。
- `AC-SNAP-018`：授权管理员经 MFA 可创建手动完整同步；重复创建被数据库唯一约束拒绝，API/中心
  重启后任务仍可领取、查询和完成，超过领取次数或 24 小时后形成稳定终态。
- `AC-SNAP-019`：手动任务下发数据不包含管理员原因、SQL、Oracle 地址、账号口令或 secret reference；
  节点只能执行本地配置与中心注册表完全匹配的固定 operation，失败仅返回稳定分类。
- `AC-SNAP-020`：默认 TCPS operation 缺少 CA/证书名时 fail closed；显式 SSH 隧道 operation 只接受
  loopback 高端口和唯一相同的 dial target，出现域名、公网监听、第二目标、Oracle TLS 字段或 listener
  redirect 时均拒绝启动。

### 22.4 人工审核

- `AC-MAN-001`：外校学生不能仅凭邮箱 OTP 自动通过，必须得到授权审核员批准。
- `AC-MAN-002`：具备摄像头能力的浏览器没有文件选择入口，用户同意后优先请求 `environment`
  摄像头；结果不会被标记为“已证明来自后置摄像头”。
- `AC-MAN-003`：本机无摄像头、无可用后置摄像头或权限被拒绝时可以扫码拍摄，两端不会重复提交
  同一申请；有本机摄像头时二维码仍可作为替代路径。
- `AC-MAN-004`：伪装图片、PDF、超限材料和其他申请的拍摄会话被后端拒绝。
- `AC-MAN-005`：审核列表不返回原始材料；只有 MFA 和 capability 满足后才能按需查看。
- `AC-MAN-006`：录取通知书批准后形成有到期时间的临时新生凭据。
- `AC-MAN-007`：外校人工学生凭据到期后资格自动失效并引导复核。
- `AC-MAN-008`：审核员不能审核自己的申请；补充、批准、驳回、材料访问和撤销都保留独立审计。
- `AC-MAN-009`：外校邮箱校验只作为审核证据，学校域名正确也不会跳过人工决定。

### 22.5 凭据与平台绑定

- `AC-CRED-001`：最后一个活动凭据到期或撤销后，聚合学生资格和 revision 立即变化，不等待用户
  token 或缓存自然过期。
- `AC-CRED-002`：同一方法重试保留每次尝试，但只产生一个满足策略的活动身份；失败尝试不会成为凭据。
- `AC-CRED-003`：同一学籍主体已属于其他活动账号时，事务返回稳定内部冲突；所有相关失败页面使用
  同一个不枚举账号的人工核查入口，不回显数据库唯一约束。
- `AC-CRED-004`：名册 `required`、`independent` 和 `conditional` 三类凭据按配置正确派生资格；配置
  变化触发带审计的受控重评估。
- `AC-CRED-005`：手机号验证和 QQ 绑定都不能单独或组合授予学生身份；内容发布明确将
  活动手机号凭据作为独立账号门槛，也不改变此结论。
- `AC-CRED-006`：姓名、手机号或相似邮箱不能触发账号或学籍自动合并。

- `AC-PHONE-001`：没有手机号的用户可以完成学生认证和查看公开内容；首次发帖时进入独立手机号
  流程，成功后恢复原草稿和发布意图。
- `AC-PHONE-002`：北航用户当次手工输入手机号，已绑定的规范学号和姓名与当前快照全部一致时，
  不发送短信，形成 `school_roster_phone_match` 凭据并通过后端写入 Casdoor；没有当次用户输入时绝不会自动绑定。
- `AC-PHONE-003`：学校号码为空、陈旧、不匹配或格式错误时不显示学校数据错误，只切换到短信路径；
  用户验证新号码后可以正常绑定。
- `AC-PHONE-004`：短信发送成功但未正确回填、验证码过期、重复消费、尝试超限或 Redis 不可用时都
  不形成 `sms_possession` 凭据。
- `AC-PHONE-005`：Casdoor `Phone` 非空但没有活动本地手机号凭据时不满足发布门槛；StuHelper PostgreSQL
  可读完整值投影与 Casdoor 一致，但任何修改、换号或解绑只能通过后端更新 Casdoor 后再同步投影。
- `AC-PHONE-006`：故障注入使 Casdoor 成功而本地激活失败，以及本地 pending 成功而 Casdoor 失败时，
  发布门槛都保持关闭；幂等对账后只激活一个正确 revision。
- `AC-PHONE-007`：换号或解绑撤销旧凭据并递增 revision，已有缓存立即失效；没有 step-up MFA、风控
  或重新验证时不能完成高风险变更；个人中心发起的变更实际写入 Casdoor 后才刷新本地投影，直接修改本地投影的
  API 或 SQL 路径被契约测试和授权测试拒绝。
- `AC-PHONE-008`：同一手机号绑定冲突不会泄露另一个账号或学校来源，所有相关失败统一提供账号找回
  入口；手机号相同不会合并账号或学生主体。
- `AC-PHONE-009`：学校目录匹配与短信 OTP 分别保留方法和保证等级，但普通发布消费方只能得到最小
  是否满足结果，不能读取号码或学校匹配状态。
- `AC-PHONE-010`：手机号、号码 HMAC、OTP、学校匹配结果和 Casdoor 响应不会进入日志、Trace、指标
  label、埋点或会话回放。

- `AC-BIND-001`：同一 QQ 号不能同时绑定两个活动 StuHelper 账号，冲突不会被最后写入者抢占。
- `AC-BIND-002`：一次性绑定码过期、重复消费、错误次数超限或上下文不一致时不能建立绑定。
- `AC-BIND-003`：解绑、换绑和管理员纠错需要 step-up MFA、风险校验和审计。
- `AC-BIND-004`：网页手工填写他人 QQ 号不能建立可信关联；只有机器人上下文、签名 token 或等价
  平台证明可以完成绑定。

### 22.6 一次性清理与无兼容切换

- `AC-MIG-001`：清理后旧 profile 学生字段、旧 credential、identity、新生/人工申请材料、旧资格事件、

- `AC-MIG-002`：用户账号、QQ 绑定、Casdoor/手机号状态、手机号凭据、群策略和普通业务数据的清理前后
  数量及关键约束一致。
- `AC-MIG-003`：全部旧私有对象进入瞬时删除队列，删除成功后对象和队列行均不存在；注入对象存储故障
  时租约可恢复、不会漏删或把对象键写入普通日志。
- `AC-MIG-004`：未执行旧 release 动作全部 stale，进行中认证型 admission 会话回到 requirements；已完成
  admission 历史不能单独授予当前学生资格。
- `AC-MIG-005`：旧 API、Web、Admin、Koishi 写入口和 profile fallback 均不存在，清理后无法再次产生
  `tencent_cloud`、旧 identity、旧 freshman application 或旧 profile verified 记录。
- `AC-MIG-006`：Casdoor 历史 `verified_student` 业务角色成员关系为零，OpenFGA、缓存和机器人
  本地的旧正向认证投影被撤销；Casdoor 用户与手机号未被删除，新学生资格只来自目标活动凭据。
- `AC-MIG-007`：down migration 明确拒绝恢复；回滚旧应用版本也不会恢复或猜测旧资格。
- `AC-MIG-008`：生产等价演练验证外键顺序、事务原子性、对象删除和非目标域不受影响；生产执行报告
  只包含零剩余/聚合计数，不包含任何个人明细或可恢复摘要。
- `AC-MIG-009`：在清理事务开始前发起一个旧写请求，以及在清理提交后由旧版本再次发起
  profile、identity、freshman、旧名册或无目标申请 ID 凭据写入，均不能在最终数据库中产生旧事实；
  目标申请签发的新凭据仍可正常写入和授予资格。
- `AC-MIG-010`：生产执行报告以聚合信息列明在线 PostgreSQL、对象存储、Casdoor、OpenFGA、缓存、
  机器人本地状态、逻辑备份、物理基准备份和 WAL 的处置结果；不包含个人明细。若任一恢复介质仍可
  恢复旧认证事实，报告必须明确标记“历史副本未清零”，且不得宣告 `DEC-012` 已完整达成。验证还应
  证明已建立不含旧认证事实的清理后恢复锚点，并且任何恢复步骤都不会重新引入旧认证事实。

### 22.7 QQ 入群准入

- `AC-ADM-001`：群策略未要求学生认证时，不会无条件进入学生认证流程。
- `AC-ADM-002`：已绑定 QQ 且已有有效学生资格的用户可以由群策略直接放行。
- `AC-ADM-003`：未绑定 QQ 时，网页手工输入他人 QQ 不能建立可信关联。
- `AC-ADM-004`：学生认证完成事件只触发 admission 重新评估，不直接命令 Koishi 解禁。
- `AC-ADM-005`：只有 admission 策略评估为 eligible 后才产生放行动作。
- `AC-ADM-006`：Koishi 执行失败时状态停留在 action pending，恢复后幂等重试。
- `AC-ADM-007`：没有 admission token 的独立认证页面不会声称某个群已通过。
- `AC-ADM-008`：凭据撤销后是否处理已在群成员，严格遵循群的持续治理开关。
- `AC-ADM-009`：并发创建相同 `platform + guild_id + platform_subject` 的进行中会话时，数据库强约束
  保证至多成功一个；应用重试复用已有会话。
- `AC-ADM-010`：会话进入 `eligible` 或 `action_pending` 后凭据撤销使 revision 失效，尚未执行的旧
  放行动作被取消或 supersede，Koishi 不能继续解禁。
- `AC-ADM-011`：自动凭据可以跳过人工审核状态直接进入 eligible；人工驳回、补充、取消和超时均按
  转换表进入明确状态。
- `AC-ADM-012`：后端、资格服务或限流依赖不可用时审核制入群始终 fail closed；配置中不存在故障
  自动同意选项。
- `AC-ADM-013`：Koishi 使用受限服务凭据调用内部接口，用户 Cookie、用户 JWT 或群管理员身份不能
  直接授予学生凭据或伪造动作成功。
- `AC-ADM-014`：SSE 在动作 claim 后、发送前或发送中断开时，动作在租约到期后可重新 claim；旧
  dispatch attempt 的迟到 ACK 不能覆盖新 attempt 或已 supersede 状态。
- `AC-ADM-015`：两个 Koishi 实例并发 claim 同一 bot 时，数据库竞争租约保证同一 attempt 只返回给
  一个实例；重复执行结果由幂等键和后端栅栏吸收。
- `AC-ADM-016`：关闭 SSE、重启 Koishi 或丢失本地缓存后，周期扫描能从 durable outbox 完成有界追赶，
  不丢动作、不重复最终平台效果。
- `AC-ADM-017`：模拟长时间断线和重连风暴时，每 bot 只有一个活动流/重连计时器，退避有上限和 jitter；
  日志按状态聚合，不为每次空扫描、心跳或普通重连写高频 info/warn。
- `AC-ADM-018`：日志审查确认不包含原始 QQ、群号、bot 号、message ID、请求/响应正文或 token；
  outbox 深度、最老年龄、ACK 延迟、dead letter 和重连状态均有低基数指标和告警。

### 22.8 契约、体验、安全和故障

- `AC-API-001`：接口变更先修改 OpenAPI 并重新生成 Go/TypeScript 类型，契约检查和 drift 检查通过。
- `AC-API-002`：用户、学校管理员、群管理员、审核员和 Koishi 对每个越权接口都得到一致拒绝，且
  不能通过批量接口或材料 URL 绕过范围限制。
- `AC-API-003`：凭据事件在数据库提交后可幂等重放；消费方使用单调 revision，不会因乱序事件恢复
  已撤销资格。
- `AC-API-004`：内容发布服务通过独立手机号门槛契约组合发布资格，不读取 Casdoor、手机号投影或
  学生快照；学生资格接口不会因手机号缺失变成未认证。
- `AC-UX-001`：完整流程可以只用键盘操作，屏幕阅读器能获知错误和进度。
- `AC-UX-002`：375 px 宽度无横向滚动，主要操作触控区域至少 44×44 px。
- `AC-UX-003`：认证入口的 Button、Input、Select、Textarea、错误提示和 CTA 使用统一组件，在默认、
  hover、focus、disabled、loading 和 error 状态都可见且可操作。
- `AC-UX-004`：信息不匹配和主体冲突使用不可枚举文案，并对所有相关失败一致展示人工核查入口。
- `AC-UX-005`：刷新和二维码交接可恢复申请状态，OTP、密码、完整证件号和拍摄帧不进入 URL 或
  浏览器持久存储。
- `AC-UX-006`：关闭动效或启用减少动态效果后流程仍完整，i18n 文案、日期、倒计时和无障碍名称一致。
- `AC-UX-007`：加载、依赖不可用、人工审核中、补充材料、成功、过期和撤销均有稳定页面状态与下一步。
- `AC-SEC-001`：自动化检查和人工审查都确认秘密值没有进入日志、Trace 和埋点。
- `AC-SEC-002`：材料列表不返回对象 key；签名 URL 只有在 capability 和 step-up MFA 都通过后短时生成，
  成功和失败访问都被审计。
- `AC-SEC-003`：证件号/OTP/SSO 枚举和爆破测试触发组合限流、递增退避与锁定；限流依赖故障时
  fail closed。
- `AC-SEC-004`：材料和旧快照按已批准保留期有界清理，清理批次可审计且不把秘密写入报告。
- `AC-SEC-005`：学校管理员、群管理员和审核员的 capability 相互隔离，审核员不能审核自己的申请。
- `AC-SEC-006`：Casdoor、短信服务、LDAP、Oracle 和校园连接器各自使用最小 secret/服务身份；配置、
  日志和管理 API 不回显秘密，轮换一个依赖不会改变学生凭据或另一个依赖的授权。
- `AC-FAIL-001`：Redis、邮件、SSO、短信、对象存储和资格服务分别故障时返回正确依赖错误，不会
  伪装成信息不匹配或业务拒绝。
- `AC-FAIL-002`：快照导入失败保留上一份成功版本，但跨过硬失效阈值后停止新的名册依赖认证。
- `AC-FAIL-003`：Koishi 离线和恢复期间待执行动作不丢失、不重复，平台执行成功前不会显示已放行。
- `AC-FAIL-004`：容量测试覆盖峰值、集中到期、快照激活和 Koishi 重连；指标、日志和告警 label 不
  包含个人身份或高基数群名。
- `AC-FAIL-005`：连接器离线、Casdoor/本地手机号投影漂移、实名校验 HMAC 密钥不可用以及 Oracle 增量条件缺失
  分别产生正确降级；系统不会用开发机代理、未登记的明文 LDAP 路径、陈旧快照或伪造第三方成功作为
  隐式恢复手段。

## 24. 验证分层

实施验证分为以下层次：

1. `VAL-001`：**单元与状态机测试**：方法资格、状态转换、过期、撤销、冲突和错误分类。
2. `VAL-002`：**Repository 集成测试**：快照原子激活、唯一约束、并发绑定和事务回滚。
3. `VAL-003`：**契约测试**：OpenAPI、生成类型、消费方资格查询、权限拒绝和领域事件。
4. `VAL-004`：**前端组件测试**：能力驱动方法、共享表单状态、错误恢复、摄像头交接和无障碍状态。
5. `VAL-005`：**浏览器 E2E**：独立学生认证、消费方回跳、邮箱收发、人工审核和 QQ admission。
6. `VAL-006`：**适配器和连接器沙箱测试**：本地实名信息 HMAC/快照比对、Casdoor/短信、学校 SSO/LDAP、
   邮件入站、Oracle 全量/增量快照、校园连接器以及各依赖故障。
7. `VAL-007`：**生产只读 smoke**：学校配置、适配器版本、连接器身份、快照新鲜度、邮件/SSO、
   Casdoor 手机号投影和 Koishi 服务凭据；不得使用真实用户学校密码探活。
8. `VAL-008`：**真实平台验收**：使用受控测试账号完成北航本地实名信息校验、北航 LDAP、真实邮件和短信、
   QQ 入群、策略重评估、Koishi 动作回写与断线恢复。测试凭据必须在运行环境以 secret 方式临时提供，不写文档、
   命令行参数、仓库、日志或测试报告。
9. `VAL-009`：本地测试、静态检查和生产 smoke 不能替代真实学校快照、学校 SSO/LDAP、邮件/短信、

## 26. 上线前待确认决策

- `GATE-001`：以下事项必须由产品 owner、学校数据负责人或安全负责人确认并留下版本化决策记录，
  不能由实现人员猜测：

| 决策 | 推荐初始方案 |
|------|--------------|
| 北航 Oracle 权威对象 | 确认实际 owner/view；需求中的 `ZHFWDB/T_XS_JBXX` 与现有接线必须统一 |
