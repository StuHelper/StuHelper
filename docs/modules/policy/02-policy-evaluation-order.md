# 航小伴授权判断顺序

航小伴的权限判断不应分散在前端、路由和业务代码里各做一遍。  
推荐统一成下面这条顺序。

## 统一判断顺序

```text
1. 认证检查
2. 应用粗粒度能力检查
3. 资源关系检查
4. 属性与业务状态检查
5. 内容整形与输出策略
```

## 1. 认证检查

先判断：

- 是否已登录 Casdoor
- token / session 是否有效

如果失败，直接拒绝。

## 2. 应用粗粒度能力检查

判断这个用户是否具备：

- 航小伴全局管理能力
- 模块管理能力

这里不处理课程、分类、具体内容对象。

## 3. 资源关系检查

判断这个用户与目标资源之间是否存在关系，例如：

- 是课程管理员
- 是课程资料编辑者
- 是评课 owner
- 是资源 owner
- 是任课教师

## 4. 属性与业务状态检查

这一层判断：

- `schoolID`
- `actorType`
- `studentVerified`
- `identityVerified`

举例：

- 只有 `schoolID=10006` 且学生认证完成的用户能查看完整课程评价
- 只有 `schoolID=10006` 且为学生，才能发布课程评价

## 5. 内容整形与输出策略

最终输出不一定只是 allow / deny。

还可能包括：

- 完整展示
- 只展示部分内容
- 允许发布但附加 `未学生认证` / `未实名认证` 标签

这一步必须放在后端完成，不能只靠前端做视觉裁剪。

## 一个典型例子

### 查看课程评价

1. 未登录：拒绝
2. 已登录但不是 `schoolID=10006` 学生认证用户：只返回部分内容
3. 已登录且是 `schoolID=10006` 学生认证用户：返回完整内容

### 发布课程评价

1. 未登录：拒绝
2. 已登录但不是学生：拒绝
3. 已登录、是学生、`schoolID=10006`、已学生认证：
   - 如果产品要求实名后才能发：继续要求 `identityVerified=true`
   - 如果产品改为允许未实名但打标签：允许发布，并打上风险标签

## 为什么这条顺序重要

如果不固定顺序，后面会出现这些问题：

- 前端说能发，后端说不能发
- 某些接口按 `isAdmin` 判断，另一些按业务权限判断
- 资源关系和属性判断混在一个巨大的 `if` 里，无法维护

所以授权必须统一入口、统一顺序、统一输出语义。
