# Koishi 控制台 Web UI 全量重构设计

## 1. 背景与目标

本设计只覆盖 `bots/koishi/plugins/stuhelper-console/client`，不涉及 `clients/web`、`clients/admin` 的页面实现，也不改动后端协议与 `console-types` 数据模型。

当前 Koishi 控制台存在三类核心问题：

1. 信息架构按数据类型堆叠，而不是按工作目标组织，导致用户无法快速判断应该去哪处理问题。
2. 首页承担了过多混杂职责，既想展示，又想配置，又想执行动作，结果主次关系失衡。
3. 组件、字号、颜色、内边距、按钮高度、说明文案风格缺乏统一规则，页面虽可用，但不具备稳定后台系统应有的一致性。

本次重构的目标是把当前控制台收敛成一个接近 Vben Admin 信息组织方式的单页后台工作区，但保持对 Koishi 控制台容器的适配：

- 视觉与交互语言向 `clients/admin` 靠拢。
- 所有元素和组件统一化，排版与布局统一化。
- 首页变成真正的综合驾驶舱，而不是“半个工作台 + 半个展示页”。
- 一级导航、二级工作区、详情抽屉、表单动作、反馈提示全部有固定模式。
- 保持真实数据流，不引入 mock、静默降级、伪成功路径。

## 2. 非目标

以下内容不在本次设计范围内：

- 不新增后端接口，不调整 `send('stuhelper-console/*')` 指令协议。
- 不修改 `../src/console-types` 中的领域对象结构。
- 不改 Koishi 外层应用壳，不尝试复刻完整 Vben 多路由后台。
- 不引入装饰性图表、运营大屏风格或提示词式文案。
- 不继续维护“总览 / 模板 / 事件 / 规则”这种旧标签体系作为最终 IA。

## 3. 总体设计原则

### 3.1 信息组织原则

页面按“工作目标”组织，而不是按“数据来源”组织。一个页面只能回答一个核心问题：

- 首页驾驶舱：现在最值得处理的是什么。
- 处置中心：高风险动作该怎么执行。
- 身份认证：准入与认证问题该怎么处理。
- 策略中心：规则、模板、绑定、权限如何维护。
- 审计检索：过去发生了什么，证据和链路在哪里。

### 3.2 视觉系统原则

视觉参考采用 Vben Admin 的后台组织方式，而不是复刻其外层框架代码：

- 明确导航层级。
- 清晰面板边界。
- 稳定的筛选条、表格、抽屉、表单结构。
- Element Plus 风格的密度与秩序感。

同时遵守本项目约束：

- 不做 dashboard hero。
- 不做浮夸运营文案。
- 不做玻璃拟态、漂浮卡片、装饰性彩色大块。
- 不让不同区域自行发明字号、颜色、圆角与控件高度。

### 3.3 实现原则

- 继续保留单路由页面 `path: '/stuhelper'`。
- 页面内部采用稳定的 section 导航，不拆成新的 Koishi 插件页面。
- 优先使用 Element Plus 与现有 Koishi 可用能力，少造新组件。
- 领域数据由现有 `use-console-page.ts` 提供，重构重点是 UI 壳、页面边界、状态流和组件组织。

## 4. 最终信息架构

### 4.1 一级导航

一级导航最终固定为以下 5 项，后续实现不得回退到旧 tab 命名：

1. `首页驾驶舱`
2. `处置中心`
3. `身份认证`
4. `策略中心`
5. `审计检索`

### 4.2 一级导航职责

#### 首页驾驶舱

只负责：

- 展示关键状态和积压。
- 排出当前优先级。
- 提供精准跳转。

不负责：

- 长表单编辑。
- 批量配置。
- 深层筛选。
- 完整执行流程。

#### 处置中心

承接所有人工复核与高风险动作执行，包含：

- `pendingReviews`
- 举报触发的人工确认
- 踢出、拉黑、升级处罚等需要人工确认的动作

这是最高频执行页，首页上的高优先级事项最终都回流到这里完成。

#### 身份认证

名称固定为“身份认证”，但职责不收窄，依然承接：

- 待认证成员
- 绑定异常
- 注册失败
- 状态不一致
- 人工放行

页面语义偏“准入治理”，但对外统一命名为“身份认证”。

#### 策略中心

统一维护：

- 关键词规则
- 命令权限
- 成员角色
- 群模板
- 群绑定

其本质是配置后台，而不是待办处理页。

#### 审计检索

统一承接：

- 近期事件
- 举报记录
- 处置历史
- 可追溯的详情证据

其核心目标是“查证”和“回溯”，而不是“操作”。

## 5. 页面壳与导航结构

### 5.1 页面整体布局

在 Koishi 现有页面容器内，重构为稳定的后台壳：

- 左侧：页面内一级导航
- 右侧：当前工作区主内容
- 顶部：当前 section 标题、说明、刷新与上下文动作
- 内容区：根据页面模板渲染
- 右侧抽屉：详情与执行区

左侧导航宽度建议固定在 `220px` 到 `240px`，视觉语言参考 Vben 菜单，但不做外层应用壳重复包装。

### 5.2 导航状态同步

一级导航和上下文跳转信息需要同步到 URL 搜索参数，至少支持以下字段：

- `section`
- `queue`
- `id`
- `source`

示例：

- `/stuhelper?section=enforcement&queue=review&id=rv_123&source=dashboard`

目标是保证刷新后仍能回到当前上下文，也保证从首页跳入目标页时能直接定位目标记录。

## 6. 页面模板统一规则

除首页外，其余页面不再自由发挥，统一收敛为 4 种模板。

### 6.1 驾驶舱页

只用于 `首页驾驶舱`：

- 顶部状态带
- 指标摘要区
- 主待办卡
- 辅助信息面板

主待办卡默认聚焦复核队列。首页上的按钮只做“进入目标页”，不在首页完成完整执行。

### 6.2 队列处理页

用于 `处置中心` 与 `身份认证`：

- 顶部筛选条
- 中部列表/表格
- 右侧详情抽屉

这是最重要的后台模板。筛选维度不同，但骨架完全一致，降低操作切换成本。

### 6.3 配置管理页

用于 `策略中心`：

- 左侧二级分类导航
- 中部配置列表
- 右侧编辑区或详情抽屉

不再把策略类对象拆散到多个独立页面。用户在一个稳定的配置后台内完成编辑。

### 6.4 审计检索页

用于 `审计检索`：

- 高级筛选区
- 结果表格
- 详情抽屉

这里的主角是“筛选”和“结果”，不是按钮矩阵。

## 7. 首页驾驶舱设计

### 7.1 首页定位

首页只解决三件事：

1. 今天有没有积压和异常。
2. 先处理什么。
3. 点进去该去哪。

### 7.2 首页模块

首页固定由以下模块组成，顺序不得打乱：

1. `状态带`
2. `指标摘要`
3. `待处理事项主卡`
4. `系统状态`
5. `快捷入口`
6. `最近事件`
7. `策略概况`
8. `最近变更`

### 7.3 首页动作规则

- 首页主卡中的 `处理` 按钮统一跳转，不直接展开复杂表单。
- 跳转目标由事项类型决定：
  - 复核项 -> `处置中心`
  - 认证/准入项 -> `身份认证`
  - 模板/绑定异常 -> `策略中心`
  - 事件/举报 -> `审计检索`
- 跳转时必须自动带上当前事项 ID、队列类型、来源页。

### 7.4 首页限制

首页禁止出现以下内容：

- 大段装饰性介绍文案
- 伪图表
- 与主流程无关的说明卡
- 重型配置表单
- 在首页完成最终风险处置

## 8. 关键页面设计

### 8.1 处置中心

#### 页面目标

以最小切换成本完成连续复核。

#### 页面结构

- 页面头部：标题、刷新、筛选摘要
- 筛选条：状态、风险等级、动作类型、来源、搜索
- 列表区：标准表格，默认按待处理优先级排序
- 抽屉区：基本信息、上下文记录、风险说明、操作区

#### 操作规则

- 主操作只保留 `执行`、`驳回`、`查看详情`
- 若动作需要备注，则在抽屉区填写
- 成功后从当前队列移除，并自动聚焦下一条待处理记录

### 8.2 身份认证

#### 页面目标

集中处理所有成员准入相关问题，而不是在多个地方分散解决。

#### 页面结构

- 筛选条：认证状态、绑定状态、失败原因、群组、关键词搜索
- 列表区：成员/状态/异常原因/最后更新时间/操作
- 抽屉区：成员信息、认证上下文、失败详情、可执行动作

#### 操作规则

- 批量动作只保留真正合理的准入操作
- 对高风险或不可逆动作使用确认层
- 人工放行、修正状态、重试类操作全部归口此页

### 8.3 策略中心

#### 页面目标

把所有规则与策略编辑统一进一个标准配置后台。

#### 二级分类

策略中心左侧分类固定为：

1. `关键词规则`
2. `命令权限`
3. `成员角色`
4. `群模板`
5. `群绑定`

#### 页面行为

- 中区列表始终展示当前分类的数据
- 右侧编辑区用于新增、编辑、查看详情
- 编辑态和浏览态的字段顺序保持一致

### 8.4 审计检索

#### 页面目标

让用户能快速回答“发生了什么、为什么发生、最后怎么处理”。

#### 页面结构

- 筛选区：时间范围、对象类型、群号、成员 ID、严重级别、关键词
- 结果区：事件/举报/处置记录统一表格或分段列表
- 详情抽屉：上下文摘要、原始字段、相关联动作、时间线

## 9. 设计系统与统一规范

### 9.1 颜色体系

优先使用 Koishi 当前主题与 Element/Vben 语义色，不自创杂色系统。文字色与面板色固定为三层：

- 主文字：高对比正文
- 正文：常规信息
- 次级说明：辅助说明

危险、警告、成功仅在以下场景中出现：

- 风险等级
- 关键状态
- 动作结果

不得用彩色来制造装饰性热闹感。

### 9.2 字号体系

本次重构后，页面内禁止随意新增字号层级。标准层级固定为：

- 页面标题：`16px`
- 面板标题：`14px / 600`
- 正文、状态、按钮、快捷入口：`12px`
- 关键数字：`24px / 600`

### 9.3 间距与高度

统一节奏：

- 模块间距：`12px`
- 面板内边距：`12px 14px`
- 常规按钮/筛选控件高度：`32px`
- 列表行最小高度：`40px`

### 9.4 组件优先级

优先复用或对齐以下组件能力：

- `ElTable`
- `ElDrawer`
- `ElForm`
- `ElDescriptions`
- `ElSkeleton`
- `ElEmpty`
- `ElButton`
- `ElTag`
- `ElScrollbar`

需要保留的自定义组件应仅限于版式封装，而不是重新造一套基础控件。

### 9.5 文案规则

- 不出现提示词式语气。
- 不出现“控制台能做什么”的营销型文案。
- 所有说明都应服务于当前动作或状态。
- 文案尽量短句，贴近后台管理系统，而不是 landing page。

## 10. 状态反馈与交互规则

### 10.1 页面状态

每个一级页面统一支持 4 种页面状态：

- 加载中
- 有数据
- 空状态
- 请求失败

规则：

- 加载中用骨架屏，不用大面积 loading 遮罩。
- 空状态给明确原因和一个主动作。
- 请求失败直接暴露错误，不做静默降级。
- 恢复数据后尽量保留筛选条件和当前位置。

### 10.2 列表状态

- hover 仅做轻微底色变化。
- 当前选中项用浅底或边框强调。
- 操作列固定在最右。
- 主信息列固定在左侧，便于扫描。

### 10.3 动作层级

所有动作分为 3 类：

1. 直接动作：刷新、切换筛选、跳转
2. 确认动作：删除、执行处置、人工放行、恢复策略
3. 表单动作：编辑规则、调整模板、修改绑定

规则：

- 能直接做的不要多弹确认。
- 不可逆或高风险动作必须确认。
- 需要填写原因或参数的必须进入表单，不做假一键。

### 10.4 抽屉结构

详情抽屉统一包含 4 个区块：

1. 基本信息
2. 上下文记录
3. 风险或异常说明
4. 操作区

不同页面不再使用不同详情结构，保证阅读顺序一致。

### 10.5 结果回写

执行类操作完成后遵守固定顺序：

1. 给出明确成功或失败反馈
2. 更新当前列表和详情
3. 不强制整页刷新
4. 若记录已处理完，自动移动到下一条可处理记录

## 11. 数据流与实现结构

### 11.1 数据来源

继续以现有 `use-console-page.ts` 为单一页面数据入口，保留以下事实：

- 数据来自 `store.stuhelperConsole`
- 动作通过 `api.ts` 中的 `send('stuhelper-console/*')` 完成
- 当前实现无需增加新的后端协议

### 11.2 前端状态分层

建议将页面前端状态分为 3 层：

1. `dataset`
   - 当前控制台业务数据
2. `navigation`
   - 当前 section、筛选条件、上下文定位信息
3. `ui`
   - 抽屉开关、当前选中行、临时表单、通知

目标是避免一个巨大的 composable 同时负责业务数据、导航、详情、表单和视觉状态。

### 11.3 目标文件边界

建议重构后的主要边界如下：

- `page.vue`
  - 只保留页面壳、导航、section 切换和抽屉挂载
- `use-console-page.ts`
  - 收敛为数据协调层，不再承载所有页面视觉逻辑
- `components/layout/*`
  - 页面壳、侧导航、工作区头部、工具栏
- `components/dashboard/*`
  - 首页驾驶舱相关模块
- `components/queue/*`
  - 队列页共用筛选条、表格、详情抽屉
- `components/policy/*`
  - 策略中心的分类导航与编辑区
- `components/audit/*`
  - 审计检索结果区与详情面板
- `styles/*`
  - tokens、layout、surface、form、table 分层，不允许回到单文件大杂烩

## 12. 实施约束

### 12.1 必须保留

- 现有 Koishi 页面注册方式
- 真实数据刷新能力
- 所有现有动作入口的业务语义

### 12.2 必须删除或避免

- 首页 hero 化结构
- 冗余提示性 copy
- 同一个对象在多个页面重复编辑
- 大量 custom 卡片样式分叉
- 右侧堆满次级面板的布局

### 12.3 Vben 对齐方式

“效仿 Vben Admin”在本项目中的具体含义是：

- 采用稳定的后台导航与工作区结构
- 使用统一的标题、筛选条、表格、抽屉、表单组合
- 保持组件密度与层级秩序

不包括：

- 复制其整套外层应用布局
- 复制其路由系统
- 复制其演示图表与装饰元素

## 13. 验收标准

### 13.1 结构验收

- 一级导航固定为 5 项，命名与职责不偏移
- 首页不再承担完整执行流程
- 其余页面能明确归入 4 种模板之一

### 13.2 视觉验收

- 页面内字号、颜色、内边距、控件高度统一
- 没有 prompt 风格、营销文案或装饰型 hero
- 不同页面共享同一套面板、表格、抽屉与表单语法

### 13.3 交互验收

- 首页点击事项能跳到正确目标页并定位到记录
- 高风险动作只在目标页执行
- 执行成功后队列能顺畅回写，不强制整页刷新

### 13.4 工程验收

- `bots/koishi/plugins/stuhelper-console/client` 内文件职责更清晰
- 样式分层稳定，视觉 token 单点管理
- `corepack yarn build` 在 `bots/koishi` 下通过

## 14. 实现顺序建议

实现顺序建议固定为：

1. 重建页面壳、一级导航和统一 token
2. 完成首页驾驶舱
3. 完成 `处置中心` 与 `身份认证` 的队列模板
4. 完成 `策略中心`
5. 完成 `审计检索`
6. 收尾统一抽屉、空态、骨架屏、通知样式

这个顺序可以最早锁定统一框架，避免后面重复返工。
